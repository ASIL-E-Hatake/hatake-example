# 初見試験（hatake を知らない AI に作らせて、動かして採点する）

> **この紙の役目**: hatake を学習していない AI が、**配った物だけ**（MCP・CLI・手引き）を
> 頼りに、頼まれた画面を作り切れるかを測る道具の説明。成績表は [results/](results/)。

hatake の道具は「AI がどこで転ぶか」を物差しにして作っています。ただ、転ぶ場所はこれまで
**作る側が推し量って**決めていました。0.9.26 の bin の不具合も、名前だけの `npx hatake` が registry の
別の道具を走らせうる件も、道具の試験は緑のままで、**新しく来た人の道を歩いてみて**初めて
見つかりました。この試験は、その「歩いてみる」を毎回機械にやらせるものです。

## 何をするか

1. まっさらなコンテナに、**画面の殻**（[30分サンプル](../apps/starter-prj/)の `web/`）と
   空の `definitions/` だけを置く。30分サンプルの定義と README（＝答え）は置かない
2. Claude Code を `claude -p` で走らせる。渡すのは頼む文（[tasks/](tasks/)の `brief.md`）と
   hatake の MCP・CLI だけ。メモリも CLAUDE.md も無い。Web の道具は渡さない
3. 終わったら、**動かして**採点する（下）
4. 記録から「どこで止まったか」を抜いて、成績表にする

## 採点（合否は全部機械）

AI の自己申告は合否に使いません。見るのは道具の終了コードと JSON、ブラウザで押した結果だけです。

| 見る所 | どう見るか |
|---|---|
| 値 | `hatake check --json` の事実が 0 件。採点の側だけが持つシナリオ（`hatake run`）で、頼んだ規則（必須・10桁・…）が効くか。エラーの**項目**を見る（文言は AI が決めるので見ない） |
| 探し方 | 一部で探すか前方で探すかは**サーバの仕事**なので、サーバが使う `buildQuery` の条件で見る（ブラウザの作り物の Repository は、いつも部分一致で見るため画面では分からない） |
| 画面 | 殻に AI の定義を載せて puppeteer で開き、`data-hatake` の印で押す（並ぶ・絞り込める・新規・修正でコードが変えられない・削除の前に聞く） |
| 殻 | `web/` を触っていない（**定義だけで作れたか**） |
| 報告 | 課題 02 だけ。`REPORT.md` の「作らなかったもの」に、枠組みの外のもの（承認・月末の処理・ログイン・メール）を1つずつ挙げたか |

採点の表は課題ごとの `task.json`。AI の作業場には置きません。

**採点の道具そのものを試す**: `evals/run.sh selftest` が、30分サンプルの定義（答え）と、
それを**わざと崩した**定義（前方一致にする・区分の絞り込みを消す・20桁にする・修正でも
直せる・殻を触る）を採点して、落ちる所が期待どおりかを見ます。通るだけを確かめると、
何も見ていない道具と見分けがつかないので。

## 止まった場所（本命の出力）

合否とは別に、記録（stream-json）から事実を抜きます（[harness/digest.mjs](harness/digest.mjs)）:

- 道具が言った規則の id と、最後まで残ったもの
- 道具が失敗した所と、そのときの文
- 枠組みの中身（`node_modules/@hatake-fw`）を読みに行ったか＝道具と手引きで引けなかった証拠
- 最初に呼んだ道具・道具ごとの回数・往復・時間

ここに出たものが、枠組みのロードマップの候補の根拠になります（枠組みに戻すのは別の PR）。

**汚染**: 見本は公開リポジトリなので、Bash から取りに行けば答えが見えます。止める仕組みは
重いので、記録を見て、取りに行った試行は**数から外して、外したと書きます**。

## 回し方

手元に要るのは Docker と bash だけです。

```bash
evals/run.sh image
```

鍵は `~/.hatake-evals.env` に1行（`claude setup-token` で取ったトークン）:

```
CLAUDE_CODE_OAUTH_TOKEN=…
```

Team / Pro / Max の席で取れます。使った分は**席の利用枠**から引かれます（成績表の費用は
Claude Code が出す目安で、請求ではありません）。道具は中身を読まずに `--env-file` で
コンテナに渡すだけです。

```bash
evals/run.sh selftest
```

```bash
evals/run.sh start 01-顧客マスタ 1
```

```bash
evals/run.sh status
```

```bash
evals/run.sh grade 01-顧客マスタ 1
```

```bash
evals/run.sh report
```

`start` はコンテナを置いたまま返ります（v0.9.27 の2課題で1回 1〜2 分。並べて回せる）。終わったら `grade`、全部終わったら
`report` が [results/<版>/成績表.md](results/) を書きます。版は `hatake.version` から読むので、
版を上げたら同じ課題を回し直すだけで前の版と比べられます。

| 変えられるもの | 既定 |
|---|---|
| `EVAL_MODEL` | `claude-sonnet-5-5` |
| `EVAL_MAX_TURNS` | 60 |
| `EVAL_TIMEOUT_SEC` | 1500 |
| `EVAL_ENV_FILE` | `~/.hatake-evals.env` |

試行は `evals/.runs/` に置きます（git には入れない。記録が大きいので）。

## 課題を足す

`tasks/<番号>-<名前>/` に `brief.md`（人が頼む文のまま）と `task.json`（採点の表）を置きます。
`extends` で別の課題の表を引き継げます（02 は 01 の表＋報告）。頼む文の**1行ずつに、動かして
確かめる所を当てる**のが決めごとで、`asks` に頼んだ文を書いておくと、成績表の「落ちた所」が
頼んだ文の言葉で出ます。

## まだやっていないこと

- 比べる条件「文書だけ（MCP 無し）」＝ MCP がどれだけ効いているかの差
- CI への常設
- 受注入力くらいの大きさの課題・モデルを替えた比較・Flutter / React の画面での採点
