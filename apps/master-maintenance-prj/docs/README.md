# 工程ごとに何を用意するか

この案件で実際に作った紙の置き場。**どの工程で何が要るか**が分かるように工程で分けてある。

## 紙の3種類

| 名前の形 | 誰が作るか | 直していいか |
|---|---|---|
| `案件の説明.md` のような普通の名前 | **人** | 人が直す。AI に書かせない |
| `出力-*.txt` | **道具**（そのまま置いただけ） | **手で直さない。** `tools/refresh-docs.sh` で作り直す |
| `definitions/*.yaml` | AI（人の依頼で） | AI が直す。人は読んで判断する |

> `出力-*.txt` を `.md` にしていないのは、**加工していない**という意味を持たせるため。
> 手で直せる形にしておくと、いつの間にか都合よく書き換わって「道具がこう言った」が
> 嘘になる。だから作り直せるようにして、CI でも見る（`tools/refresh-docs.sh --check`）。

人が AI に**何を投げたか**は [手順/](../手順/) にある（この `docs/` は成果物、あちらは操作）。

---

## 1. 要件定義

**目的**: 何を作るかと、**hatake で作れないもの**を先に分ける。

| 紙 | 誰が | 何のために |
|---|---|---|
| [案件の説明.md](1-要件定義/案件の説明.md) | 人 | 知っていることを普通の日本語で。書式は要らない |
| [出力-枠組みの外の仕分け.txt](1-要件定義/出力-枠組みの外の仕分け.txt) | `hatake where --from` | 認証・締め処理・採番など**定義に書けないもの**を先に出す |

**この工程を抜かすと**: AI が画面の中に業務ロジックを書き始める。あとで剥がすのは高い。

**終わりの判定**: 「外」と出たものが全部、前書きの `premises` か `logic` に載っている。

> この案件では **認証が「枠組みの外」** と出た。だから画面に認証は無く、`node-src` の担当。

---

## 2. 設計

**目的**: 定義（画面の仕様）を作る。**決めていないことを人に返す**のもこの工程。

| 紙 | 誰が | 何のために |
|---|---|---|
| [definitions/hatake.project.yaml](../definitions/hatake.project.yaml) | **人** | 案件の前書き。**定義を書く前に AI に読ませる1枚**（用語・決めごと・できないこと） |
| [definitions/app.yaml](../definitions/app.yaml) | AI | 画面の定義。人は1行も書いていない |
| [画面一覧](2-設計/画面一覧.md) / [画面遷移図](2-設計/画面遷移図.md) / [画面設計書](2-設計/画面設計書/) / [API一覧](2-設計/API一覧.md) / [権限マトリクス](2-設計/権限マトリクス.md) | **生成物** | **人が読む設計書**。定義から起こすので腐らない（`node tools/build-design-docs.mjs`） |
| [出力-読み返しと助言.txt](2-設計/出力-読み返しと助言.txt) | `hatake check` | 事実（警告）・読み返し・好み（助言）を1枚で |
| [出力-残っている問い.txt](2-設計/出力-残っている問い.txt) | `hatake ask` | **人が決めないと決まらないこと**。0件になるまで人が答える |

**この工程を抜かすと**: 「それっぽいけど誰も決めていない設計」が残る。半年後に揉める。

**終わりの判定**:

```bash
npx hatake check definitions/app.yaml --project definitions/hatake.project.yaml
```

- 事実（警告）が **0件**
- 残っている問いが **0件**
- 助言は0でなくてよい（好みなので、案件の判断で残す）
- **設計資料がそろっている**（`node tools/build-design-docs.mjs --check` が通る）

> 人に渡す1枚が要るなら `npx hatake design`（意図と突き合わせた設計書を刷る）。

## 3. 実装

**目的**: 定義が要求しているものを、アプリ側に用意する。

| 紙 | 誰が | 何のために |
|---|---|---|
| [出力-登録が要るもの.txt](3-実装/出力-登録が要るもの.txt) | `hatake refs --needs-registration` | Repository・プラグイン・出す口・役割の**一覧**。これを埋めるのが実装 |
| [../definitions/hatake-registry.json](../definitions/hatake-registry.json) | `hatake registry <実装>` | 実装のソースを読んで「登録済みのもの」を作る（**手で書かない**） |
| [出力-画面の外との辻褄.txt](3-実装/出力-画面の外との辻褄.txt) | `hatake validate --registry` | 上の2つの突き合わせ。登録し忘れが0件か |

**この工程を抜かすと**: **画面は出るのにデータが来ない／押しても何も起きない**。
定義もスキーマも通るので、動かすまで気づけない。

**終わりの判定**: `validate --registry` が登録し忘れ0件。

> 実装を**読める形で書く**必要がある。`restRepositories(collections: {...})` のように
> 関数の戻り値に名前を隠すと `hatake registry` が読めず、「読めなかった登録が2件
> あります」と言われて一覧が穴あきになる（実際そうなった）。穴あきの一覧を渡すと、
> 突き合わせが**言えるはずのことを言えなくなる**。

## 4. テスト

**目的**: 「書ける」ではなく「**その値でどうなるか**」を確かめて、**納品できる形**で残す。

| 紙 | 誰が | 何のために |
|---|---|---|
| [ケース一覧.md](4-テスト/ケース一覧.md) | 人＋AI | **確かめることの全部**。項番から結果へ辿れる。**確かめていないもの**も書く |
| [出力-シナリオ結果.txt](4-テスト/出力-シナリオ結果.txt) | `hatake run` | 値の合否（31件） |
| [出力-試していない所.txt](4-テスト/出力-試していない所.txt) | `hatake run --cover` | まだ試していない分岐（**0件**） |
| [出力-APIテスト結果.md](4-テスト/出力-APIテスト結果.md) | `tests/api/run.mjs` | API の実行記録（20件・投げたもの／返ってきたもの） |
| [出力-画面テスト結果.md](4-テスト/出力-画面テスト結果.md) | `tests/screen/shots.mjs` | 画面の記録（6枚・項番つきスクリーンショット） |

**この工程を抜かすと**: 検証も助言も「書ける」ことしか見ていないので、
**その値でいくらになるか・押せるか**は誰も確かめていない状態で出荷することになる。

**終わりの判定**:

```bash
docker compose up -d
bash tools/run-tests.sh
```

- 値・API が全件期待どおり
- `--cover` が **0件**
- 画面のスクショが全枚数撮れていて、**目で見て確かめること**を満たしている（ここだけ人）

> **エビデンスは hatake の担当ではない。** 枠組みが持つのは「定義から試験を起こす」
> 「動かして答えを見る」までで、**納品する紙の様式は案件ごとに違う**ので `tests/` に
> 自分で作る（認証と同じ線の引き方）。作り方と AI への頼み方は
> [手順/05](../手順/06-テストしてエビデンスを残す.md)。

## 工程をまたいで効くもの

| | |
|---|---|
| [CLAUDE.md](../CLAUDE.md) | AI が毎回読む。**前書きから生成した節**が入っている（`hatake project --agents`） |
| [.claude/commands/](../.claude/commands/) | 定型の依頼（スラッシュコマンド）。毎回同じ文を打たなくて済む |
| [tools/refresh-docs.sh](../tools/refresh-docs.sh) | `出力-*.txt` を作り直す。CI が `--check` で古さを見る |
| [tools/build-design-docs.mjs](../tools/build-design-docs.mjs) | 設計資料を定義から作り直す（`--check` で古さを見る） |
| [まとめ/](まとめ/) | **この案件を通してみた記録**（工数の比較・起きた問題・課題）。導入を検討する人向け |
