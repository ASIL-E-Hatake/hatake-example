# 途中で起きた問題と、どう直したか

この案件を作る間に踏んだものを**全部**並べます。見栄えのために減らしていません。

導入を検討する人にとっては、**うまくいった話より、どこで転ぶかとその深さ**の方が
役に立つはずなので。

## 内訳

| 出どころ | 件数 | 深さ |
|---|---|---|
| フレームワーク本体の不具合 | 3 | 直すのに半日／1件。どれも**外から使わないと出ない**種類 |
| 使う側の書き間違い（道具が止めてくれた） | 4 | 数分 |
| 使う側の書き間違い（**道具が止めてくれなかった**） | 2 | 半日（テストを書くまで気づけない） |
| 環境まわり（Docker・Flutter） | 4 | 数十分 |

---

## A. フレームワーク本体の不具合

### A-1 降順の指定が黙って無視されていた

`buildQuery` が `sortAscending` の**文字列 `"false"`** を昇順として読んでいました。
REST の契約は「クエリ文字列で送る」と決めているので、**手引きどおりに書いたサーバが
降順を頼まれても昇順で返す**。画面には並びが出るので気づけません。

**なぜ出なかったか**: リポジトリの中の試験は、クライアント側とサーバ側を**別々に**
見ていて、契約の両端をつなぐ試験が無かった。外から一気通貫で使って初めて出ました。

**対応**: TypeScript と Java の両方を直し、共有フィクスチャに文字列の場合を足して
3版で固定（v0.9.0 に収録）。

### A-2 検証のパラメータ名を間違えても、黙って効かない

```yaml
- { type: pattern, value: "^[0-9]{6}$" }   # 正しくは pattern:
```

`validate` も `check` も**警告ゼロ**で通り、`12A456` が6桁の規則を素通りしました。
**テストを書くまで誰も気づけません。**

**対応**: 新しい警告（`validator-missing-param`）を足しました。何を書いてしまったかも
名指しします。

### A-3 一覧にコードがそのまま出ていた

入力欄では「法人」「取引中」と出るのに、一覧では `corp` / `active` と生のコード。
同じ画面で同じ項目が2つの顔を持っていました。**納品用のスクリーンショットに並んで**
気づきました。

**対応**: 列に `options` を書けるようにする案もありましたが、**同じことを2か所に
書かせない**ために、同じ画面の入力欄・検索条件から引く形にしました（DSL のキーは増やさない）。

## B. 書き間違いを、道具が止めてくれたもの

**どれも動かす前に止まりました。**「書けるけれど意図どおり動かない」種類です。

| 何を書いたか | 道具が何と言ったか |
|---|---|
| 一括の上限を 100 件（1ページは 50 件） | 「選べるのは画面に出ている行だけなので、**この上限は一度も効きません**」 |
| `soft-delete` という問いの印 | 「**そんな問いはありません**」（`ask --kinds` で引ける正しい印を使え） |
| 採番を「枠組みの外」と書いた | 「`numbering` は**サーバの担当**です。区分が違います」 |
| 辞書の見出しを「区分」にした | 「`employmentStatus` に supplier が入っていません」（在籍区分まで巻き込んだ） |

**最後の1つは道具の言い分が正しくない**例でもあります（辞書の書き方が広すぎた）。
助言は好みなので、**直すかどうかは人が決める**という設計がここで効きました。

---

## C. 道具が止めてくれなかったもの

| | どう気づいたか |
|---|---|
| `pattern` の書き間違い（A-2） | **テストを書いて**初めて出た |
| 守れない命名規則（`naming.suffix.number: Amount`） | 助言が鳴り続けて、こちらが折れた |

2つ目は不具合ではありません。**守れない決めごとを書くと、助言が鳴りっぱなしになって
そのうち誰も読まなくなる**という教訓です。決めごとは守れるものだけ書く。

---

## D. 環境まわり

| | |
|---|---|
| API が定義を見失って起動しない | Dockerfile がリポジトリと**違う階層**で置いていた。手元と同じ形に直した |
| 部署を消したら**サーバごと落ちた** | Express 4 は async の失敗を拾わない。包んで、制約違反は業務の言葉で返すようにした |
| 画面のアイコンが全部**豆腐（□）** | `pubspec.yaml` に `uses-material-design: true` が無く、フォントが同梱されていなかった |
| テストが**2回目から結果が変わる** | postgres はデータ置き場をボリューム宣言しているので、作り直しても中身が残る（`--renew-anon-volumes` が要る） |
| 納品用のスクショが**真っ白** | 「未ログインで撮る」件の判定が初期値と一致して、**ページを開かずに撮っていた** |

最後の2つは、**エビデンスを作る側の落とし穴**です。どちらも「見た目には成功している」
ので、紙をよく見るまで気づきません。

---

## 直し方の傾向

| | |
|---|---|
| **道具が止めたもの** | その場で直る（数分）。止めてくれた理由も一緒に出るので、調べる時間が要らない |
| **道具が止めなかったもの** | テストを書くまで出ない。**だからテストを省くと危ない**、が具体的に分かった |
| **本体の不具合** | 外から一気通貫で使うと出る。中の試験は端ごとに見ているので、境目が抜ける |

## 使ってみた人への示唆

1. **`hatake check` の警告は必ずゼロにする。** 事実なので、直すのに業務の判断が要りません
2. **テストを省かない。** 道具が止められない範囲（`pattern` の書き間違いなど）がある
3. **助言は全部当てない。** 好みなので、案件で要らないものは切る
4. **エビデンスの紙は必ず目で見る。** 生成できても、中身が正しいとは限りません
