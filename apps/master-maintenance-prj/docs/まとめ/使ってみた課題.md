# 使ってみて分かった課題

**直っていないもの・向いていないもの**を並べます。導入を検討する人が見るべきは
ここだと思うので、良かった点より先に置きます。

## 1. 枠組みが持たないもの（設計として持たない）

これは不具合ではなく**決めごと**ですが、**導入すると自分で作ることになる**ものです。

| | どこに書くことになったか | 量 |
|---|---|---|
| 認証・ログイン | `node-src/src/auth.js` `flutter-src/lib/login_page.dart` | 約 150 行 |
| 役割による**本当の遮断** | `node-src/src/authz.js` | 約 50 行 |
| 監査（誰が・いつ・何を） | `node-src/src/audit.js` | 約 15 行 |
| 同時更新の弾き方 | `node-src/src/routes/masters.js` | 約 20 行 |
| 一括の中身（部分失敗の始末） | `node-src/src/routes/bulk.js` ＋ Flutter のプラグイン | 約 100 行 |
| **納品用の設計資料を並べる紙** | `tools/build-design-docs.mjs` | 約 280 行 |
| **納品用のエビデンス**（スクショ・API の記録） | `tests/` | 約 600 行 |

**合計 1,200 行ほどが「枠組みの外」**。ただし**案件をまたいで使い回せる**ものが大半です
（認証・監査・エビデンスの道具は2本目でほぼそのまま動くはず）。

> 判断材料: **1本目は枠組みの外を作る分が乗る**。効果が出るのは2本目から、という前提で
> 見積もってください。

## 2. 直っていないもの

| | 困り方 | 回避 |
|---|---|---|
| `hatake openapi` が **app 定義を読めない** | 画面が4枚あっても1枚ずつ切り出して渡す必要がある | API 一覧は Repository の契約から組んだ（むしろ正しい粒度だった） |
| `explain --roles --matrix --markdown` が Markdown にならない | 幅を揃えた文字が出るだけ | コード囲みに入れて貼った |
| `hatake shot`（定義から画面の写真） | **未実装**（ロードマップにはある） | ブラウザで撮る道具を自分で作った（約 200 行） |
| 一覧の**並べ替えできる列**が定義から読めない | 設計書に「どの列が並べ替えられるか」を出せない | 画面設計書には出ていない（`explain` が言わない） |

## 3. 学習コストがかかったところ

| | |
|---|---|
| **定義に書けることと書けないことの線** | 最初は「認証も定義で書けるのでは」と思う。`hatake where` に聞けば済むが、**聞くことを知らないと分からない** |
| **問い（`ask`）の印を正しく書く** | それっぽい名前を書くと落とされる。`ask --kinds` を引く癖がつくまで数回転ぶ |
| **助言をどこまで当てるか** | 全部当てると定義が膨らむ。好みなので判断が要るが、**判断の基準は自分で持つ**しかない |
| **解析後のモデルの名前が YAML と違う** | `key` → `keyField`、`type` → `kind`。アプリ側を書くときに一度つまずく |

## 4. 向いていない案件

| | なぜ |
|---|---|
| 画面そのものが要件（凝った UI・独自の操作感） | 定義で書けるのは「業務画面の形」。外れると全部プラグインになる |
| 1〜2画面で終わる | 枠組みの外を作る分が回収できない |
| 納品物が要らない（社内ツール） | いちばん効くところ（設計書・エビデンスの自動生成）が空振りする |
| 既存画面への部分導入 | この案件では試していない（移行の手順は未検証） |

## 5. 試していないこと

**紙に書いていないことは、やっていないのと同じ**なので並べます。

| | |
|---|---|
| 親子明細（受注入力のような画面） | 2本目でやる |
| 帳票（PDF）・ダッシュボード | 同上 |
| ウィザード（ステップ入力） | 同上 |
| 既存システムからの移行 | 未検証 |
| 複数人での同時開発 | 1人で作った |
| 性能（データ量・同時接続） | 48件・10人想定。**測っていない** |
| Flutter 以外の画面（Vue / React） | 枠組み側が未対応（ロードマップにはある） |
| ブラウザの種類 | Chrome だけ |

## 6. それでも良かったところ

課題を先に置いたので、最後に。

| | |
|---|---|
| **決めていないことが先に出る** | `ask` が6件返した。手で作ると**実装が終わってから**出てくる種類の話 |
| **黙って効かない書き方を止められる** | 一括の上限が「一度も効かない」設定を、動かす前に言われた |
| **設計書とエビデンスが腐らない** | 定義から作り直せるので、直したら作り直すだけ |
| **画面とサーバがズレない** | 同じ定義で検証する。2か所に書くと必ずどちらかが古くなる |
| **道具が嘘をつかない** | 「読めなかった登録が2件あります」と言って**黙って落とさない**。一覧が穴あきのまま「問題なし」と言われるより、ずっと信用できる |
