# 工数の比較（人だけ / AI だけ / hatake + AI）

導入を検討する人が**自分の数字に置き換えられる**ように、計算の中身を全部出します。

| | 人の時間 | 実測か |
|---|---|---|
| 人だけ（AI を使わない） | 21.0 人日 | 見積もり |
| **AI だけ**（フレームワーク無しで Claude Code） | 8.5 人日 | 見積もり |
| **hatake + AI** | **3.75 人日** | **実測** |

> **正直に先に**: 実測は「hatake + AI」だけです。ほかの2つは**見積もり**で、
> 同じものを実際に作って測ってはいません。**根拠は全部出す**ので、自社の単価と
> 生産性で置き換えてください。

---

## 何を作った案件か

社内マスタメンテナンス（社員・部署・取引先の3マスタ・4画面）。
権限3種・複雑な検索・一括処理・監査つき。画面（Flutter Web）と API（Node）の両方。

実際に動きます（`docker compose up`）。→ [案件の README](../../README.md)

| | 行数 | 誰が書いたか |
|---|---|---|
| 案件の説明 | 57 | **人** |
| 案件の前書き（`hatake.project.yaml`） | 149 | **人**（下書きは AI） |

**人が書いたのは 206 行。** 残りの約 4,800 行は AI が書いたか、定義から生成されたもの。

## 人だけで作った場合（見積もり）

同じものを人が手で作る前提。**1人日 = 7時間**、画面まわりに慣れた開発者1人で計算します。

| 工程 | 作業 | 人日 | 根拠 |
|---|---|---|---|
| 要件定義 | 要件のヒアリングとメモ | 1.0 | AI でも人でも同じ（人にしかできない） |
| 設計 | 画面設計書 4枚 | 2.0 | 1画面 0.5人日（項目表・条件・権限を書く） |
| 設計 | 画面一覧・遷移図・API 一覧・権限表 | 1.0 | 並べて図を描く |
| 実装 | 画面 4枚（検索・一覧・入力・権限・一括） | 6.0 | 1画面 1.5人日 |
| 実装 | API（CRUD 3本・認証・一括・監査） | 4.0 | |
| 実装 | 環境（Docker・DB・初期データ） | 1.0 | |
| テスト | ケース設計 | 1.5 | 57件ぶんの条件と期待を書く |
| テスト | 実施とエビデンス（スクショ・API の記録） | 2.5 | **手で撮って貼る**のがここ |
| 手直し | 仕様の食い違い・レビュー指摘 | 2.0 | |
| **合計** | | **21.0 人日** | |

## 人＋AI（この案件で実際にかかったもの）

| 工程 | 人がやったこと | 人の時間 | AI の作業 |
|---|---|---|---|
| 要件定義 | 案件の説明を書く（57行） | **1.0 人日** | 枠組みの外を仕分ける |
| 設計 | 前書きを育てる・**用語と決めごとを直す** | **0.5 人日** | 定義を書く・自分で読み返す |
| 設計 | **問い6件に答える**（同時更新・一括の失敗・監査…） | **0.5 人日** | 答えを前書きに書く |
| 設計 | 生成された設計書を読む | **0.25 人日** | 設計資料5種を生成 |
| 実装 | 出てきたコードを読む・繋ぎの判断 | **0.5 人日** | 画面・API・Docker |
| テスト | **何を確かめるかを決める**・記録を読む | **0.5 人日** | 57件を書いて回す・記録を作る |
| 手直し | 踏んだ問題の判断 | **0.5 人日** | 直す |
| **合計** | | **3.75 人日** | |

## 差

| | 人だけ | 人＋AI | 差 |
|---|---|---|---|
| 人の時間 | 21.0 人日 | **3.75 人日** | **▲17.25 人日（82% 減）** |

（**フレームワーク無しで AI だけ**に作らせた場合との比較は[下の節](#もう1つの比べ方フレームワークを使わずに-ai-だけで作る)に足しました。）

**自分の数字に置き換える式:**

```
削減率 = 1 −（人がやる工程の合計 ÷ 全工程の合計）

この案件では、人に残ったのは
  ・要件を書く（1.0）        … AI でも減らない
  ・決めごとを判断する（1.0） … AI に任せてはいけない
  ・読んで確かめる（1.75）    … 量に比例して増える
```

> **減らないところが2つある**のが肝心です。**要件を書く**のと**業務の判断をする**のは
> 人の仕事として残ります。減るのは**書く作業**（設計書・コード・テスト・資料）。

## もう1つの比べ方：**フレームワークを使わずに AI だけで作る**

「人だけ」と比べても、いまどきそうは作りません。**同じものを Claude Code に
フレームワーク無しで作らせたら**どうなるかを足します。

> ⚠️ **ここは想定です。** 実際に作って測ってはいません（上の「人＋AI」だけが実測）。
> 数字は下の根拠から計算したもので、根拠も全部出します。

### 前提

- 同じ4画面・同じ業務（権限3種・複雑な検索・一括・排他・監査）
- Flutter + Node + PostgreSQL も同じ
- AI は Claude Code。規約は人が用意して毎回読ませる
- **枠組みの外**（認証・監査・一括の中身・Docker）は**どちらでも同じだけ要る**ので、
  差が出る所だけを比べる

### AI が書く量

| | hatake + AI | AI だけ | 根拠 |
|---|---|---|---|
| 画面 | 定義 **345 行** | Flutter **約 2,750 行** | 汎用の Renderer は crud 1枚 559 行・search 308・detail 117（実測）。専用に書けば少し減るが、入力欄・検証の表示・ページ送りは画面ごとに要る |
| 画面の配線 | **約 450 行** | （画面のコードに含む） | Repository の対応表・プラグイン・出す口 |
| API | 認証など **約 450 行** | 同じ 450 ＋ **約 650 行** | CRUD 3本ぶんの検索の組み立て・**検証の書き直し**・返す形の整形 |
| **差が出るところの合計** | **約 795 行** | **約 3,400 行** | **4.3 倍** |

**ご予想のとおり、AI が書く量は4倍以上**になります。しかも増えるのは
「画面ごとに同じようなものを書き直す」部分です。

### AI が読む量（ここが予想と少し違います）

**最初は hatake の方が重い**です。DSL の書き方を引く必要があるので。
**逆転するのは2画面目から**で、そこからは差が開き続けます。

| | hatake + AI | AI だけ |
|---|---|---|
| 1画面目 | 前書き 149 ＋ CLAUDE.md 130 ＋ **引き物 300〜500**（`reference` / `examples`） | 規約メモ 100〜200 |
| 2画面目 | 上＋**既存の定義 120 行** | 規約＋**既存の画面 500 行** |
| 3画面目 | 上＋既存の定義 240 行 | 規約＋既存の画面 1,000 行 |
| 4画面目 | 上＋既存の定義 300 行 | 規約＋既存の画面 1,500 行 |
| **4画面の合計（概算）** | **約 2,500 行** | **約 3,500 行** |

**なぜ逆転するか**: hatake 側で「前の画面」として読むのは**定義**（1画面 60〜120 行）
ですが、AI だけの側で読むのは**コード**（1画面 500 行前後）。揃えるために前の画面を
読まないといけないのは同じでも、**読む対象の大きさが4〜5倍違います**。

そしてこの差は**画面数の2乗で効きます**（n 画面目に n-1 画面ぶん読むので）。

> **引き物は毎回ではありません。** hatake は仕様書を読ませる代わりに
> **引かせる**作りなので（`reference` / `examples` / `rules`）、必要なキーだけが
> 文脈に乗ります。2画面目以降は引く回数も減ります。

### 往復の回数（ここがいちばん効きます）

行数より効くのが**直しの往復**です。

| | hatake + AI | AI だけ |
|---|---|---|
| 書き間違いを誰が見つけるか | **機械**（95種類の警告）。書いた直後 | **人**（レビュー）か**動かしたとき** |
| 「書いたのに効かない」 | 言う（一括の上限が効かない等） | **言わない** |
| 決めていないこと | `ask` が12種類から出す | **出ない**（実装が終わってから気づく） |
| 画面とサーバのズレ | **起きない**（同じ定義を読む） | 検証を2か所に書くので**必ず起きる** |
| 1画面あたりの直しの往復 | **1〜2回**（警告ゼロまで） | **3〜5回**（レビュー指摘→直し→再レビュー） |

この案件で機械が止めたのは4件、止められなかったのは2件でした。
**AI だけなら6件とも人がレビューで見つける**ことになります。

### 文脈のコスト（自社の単価を入れてください）

行数をトークンに換算します（**日本語混じりのコード/文書は 1行 ≈ 20 トークン**として計算。
自社で測った係数に置き換えてください）。

| | hatake + AI | AI だけ | 差 |
|---|---|---|---|
| 読む（入力） | 約 2,500 行 → **5万トークン** | 約 3,500 行 → **7万トークン** | 1.4 倍 |
| 書く（出力） | 約 795 行 → **1.6万トークン** | 約 3,400 行 → **6.8万トークン** | **4.3 倍** |
| 往復の回数 | 4画面 × 1〜2回 ＝ **6回** | 4画面 × 3〜5回 ＝ **16回** | **2.7 倍** |
| **往復ぶんを掛けた総量** | **約 40万トークン** | **約 220万トークン** | **約 5.5 倍** |

```
AI のコスト = 総トークン × 自社の単価

※ 出力トークンは入力より単価が高いので、**出力が4.3倍**であることが効きます。
※ 直しの往復は毎回「それまでの文脈」を運ぶので、回数が増えると総量は掛け算で増えます。
```

### 人の時間

| | 人だけ | AI だけ | hatake + AI |
|---|---|---|---|
| 要件を書く | 1.0 | 1.0 | 1.0 |
| 設計 | 3.0 | **1.5**（AI が書いた設計書を人が直す） | **1.25** |
| 実装（読む・判断する） | 11.0 | **2.5**（3,400 行を読んでレビューする） | **0.5** |
| テスト | 4.0 | **2.0**（ケースを人が考える。`--cover` が無い） | **0.5** |
| 手直し | 2.0 | **1.5**（往復が多い） | **0.5** |
| **合計** | **21.0 人日** | **8.5 人日** | **3.75 人日** |

**AI だけでも 21.0 → 8.5 人日（▲60%）まで減ります。** そこからさらに
**8.5 → 3.75 人日（▲56%）** 減るのが、フレームワークの取り分です。

> **人の時間がいちばん残るのは「読んでレビューする」ところ**です。AI だけの場合は
> 3,400 行を読む必要がありますが、hatake なら読むのは**定義 345 行**で足ります
> （残りは生成物なので、疑ったときだけ見る）。

### 数字にならない差

| | hatake + AI | AI だけ |
|---|---|---|
| **設計書** | 定義から生成（腐らない） | AI が書く → **コードと二重管理**。直すと片方が古くなる |
| **テストのケース漏れ** | `--cover` が0件になるまで機械が言う | **誰も言わない**（人が気づくまで） |
| **画面間の一貫性** | 定義の語彙が同じなので揃う | 4画面目で1画面目とズレる（読み直させれば揃うが、その読む量が上の表） |
| **半年後の引き継ぎ** | 定義 345 行を読めば分かる | 3,400 行を読む |

### AI だけの方が良いところ（公平に）

| | |
|---|---|
| **学習コストがゼロ** | DSL を覚えなくていい。初日から書ける |
| **見た目が自由** | 定義で書けない画面（凝った UI）でも作れる |
| **枠組みの不具合を踏まない** | この案件では3件踏んだ（半日／件） |
| **依存が1つ減る** | 版を上げる・tag を切るといった運用が要らない |

**1〜2画面で終わる案件なら、AI だけの方が速い**と思います。
分かれ目はだいたい**3画面**（学習コストと枠組みの外を作る分が回収できるあたり）。

## 画面が増えるとどうなるか

**人だけは画面数にほぼ比例**、**人＋AI は緩やかに増える**（読む時間だけ増えるので）。

| 画面数 | 人だけ | AI だけ | hatake + AI | 人だけ比 |
|---|---|---|---|---|
| 1〜2 | 8.0 | **3.0** | 3.5 | AI だけが速い |
| 4（この案件） | 21.0 | 8.5 | **3.75** | 82% 減 |
| 10 | 45.0 | 18.0 | **6.0** | 87% 減 |
| 20 | 85.0 | 36.0 | **9.5** | 89% 減 |

> 10画面・20画面は**この案件からの外挿**です（実測ではありません）。
> 画面1枚あたり、人だけは +4.0 人日、AI だけは +1.6 人日、hatake + AI は
> +0.25〜0.4 人日（読む時間）で計算。
> **2本目の案件を作ったら、この表を実測で置き換えます。**

**AI だけの線が人だけより緩やかで、hatake の線よりは急**なのが要点です。
AI だけでも書く時間は減りますが、**画面ごとに同じものを書き直す**ので、読んで
レビューする時間が画面数に比例して増えます。

## 効く条件・効かない条件

| よく効く | 効きにくい |
|---|---|
| 画面の形が決まっている（マスタ・検索・一覧・入力） | 画面そのものが要件（凝った UI・独自の操作感） |
| 画面数が多い | 1〜2画面で終わる |
| 同じ規則をフロントとバックの両方で守りたい | 画面だけ・API だけ |
| 権限や一括処理など**決まりごとが多い** | 決まりごとが少ない |
| 納品物（設計書・エビデンス）が要る | 動けばいい |

**画面の中身より「決まりごとの多さ」で効きます。** 権限・検証・一括の上限・監査は、
手で書くと画面とサーバの2か所に散って必ずズレますが、定義なら1か所です。

## 数字にしにくいが大きいこと

| | |
|---|---|
| **設計書が腐らない** | 定義から生成するので、直したら作り直すだけ。手で書いた設計書は3か月で嘘になる |
| **画面とサーバがズレない** | 同じ定義で検証する。手で書くと必ずどちらかが古くなる |
| **決めていないことが先に出る** | `hatake ask` が6件返した。手で作ると**実装が終わってから**出てくる |
| **黙って効かない書き方を止められる** | 一括の上限が「一度も効かない」設定になっていたのを、動かす前に言われた |

## この数字の限界

- **1案件・1人の結果**です。2本目で検証します
- 「人だけ」と「AI だけ」は見積もりで、**実際に作って測った値ではありません**
  （実測は「人＋AI」だけ）。特に「AI だけ」は、同じものを本当に作らせて比べるのが
  いちばん確かなので、**やる価値があります**
- AI の待ち時間（生成を待つ時間）は人の時間に数えていません。実際は読みながら待てます
- 慣れの分は入っていません。**1本目はここに書いた手順を作りながらなので、2本目はもっと短くなるはず**です
