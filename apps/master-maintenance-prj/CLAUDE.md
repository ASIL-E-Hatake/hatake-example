# 社内マスタメンテナンス（AI 向けの指示）

このフォルダで作業するときに最初に読む紙。

## この案件の作り方

**画面は定義（YAML）で作る。Flutter / Vue のウィジェットを手で書かない。**

- 定義: `definitions/app.yaml`（画面4枚）
- 前書き: `definitions/hatake.project.yaml` … **定義を書く前に必ず読む**
- 手順: `手順/` … 人が何を投げたか。同じ形で続ける
- 工程ごとの成果物: `docs/`

道具は `npx hatake <コマンド>`。仕様書は読まなくていい（**引ける**ようになっている）:

| 迷ったら | 引くもの |
|---|---|
| このキーはどこに書く？型は？ | `npx hatake reference <キー名>` |
| こういう画面の例は？ | `npx hatake examples <やりたいこと>` |
| この警告は何？ | `npx hatake rules <規則名>` |
| これは hatake で書ける？ | `npx hatake where <やりたいこと>` |

## 守ること

1. **定義を書いたら必ず `check` を通す。**
   ```bash
   npx hatake check definitions/app.yaml --project definitions/hatake.project.yaml
   ```
   事実（警告）が0件になるまで直す。**助言（好み）は勝手に当てない**（人に聞く）。

2. **前書きに書いていないことを定義に足さない。**
   言われていない項目・ボタンを「あると便利だろう」で足さない。

3. **`hatake ask` が返した問いに勝手に答えない。**
   業務の判断なので人が決める。答えを前書きに書くのは人が決めたあと。

4. **枠組みの外のものを画面に実装しない。**
   認証・監査・採番・与信の判断はこの案件では外に置いた（下の「業務ロジックの置き場」）。
   画面に出すのは**結果だけ**。

5. **`docs/**/出力-*.txt` を手で直さない。** 道具の出力をそのまま置いた紙。
   作り直すのは `tools/refresh-docs.sh`。

6. **定義を直したら `tools/refresh-docs.sh` を回す**（`docs/` の出力が古くなるので）。

## この案件について

> ここは `definitions/hatake.project.yaml` から生成した節です（`npx hatake project --agents`）。
> **直すときは前書きを直して貼り直す**（同じことを2か所に書くと必ず食い違う）。

人事部と購買部が使う社内マスタの管理画面。社員・部署・取引先の3つを、情シスに 依頼せず自分たちで直せるようにする。いまは Excel で管理している。

**使う人**

- 情シス（admin・2人）。全マスタを直せる
- 人事（hr・5人）。社員と部署を直せる。取引先は見るだけ
- 一般（viewer・全社員）。どのマスタも見るだけ

**業務の前提（できないことも含む）**

- ログインは hatake の外。画面は定義で作るが、資格を確かめるのは API 側。
- 認証は当面このシステムが ID とパスワードを持つ。将来 Active Directory に差し替える。
- 社員番号は採番しない。人事が決めた番号を手で入れる（既存の Excel と揃えるため）。
- 退職者は消さない。在籍区分を「退職」にするだけ。
- 監査（誰がいつ何を直したか）は API 側で残す。画面は残さない。
- 与信限度額の判断（この取引先にいくらまで）は購買部の別システムが正。ここでは記録するだけ。

**外の相手**

- `employeeRepository` … 社員マスタ（この案件の API）（聞く相手: 情シス）
- `departmentRepository` … 部署マスタ（この案件の API）（聞く相手: 情シス）
- `supplierRepository` … 取引先マスタ（この案件の API）（聞く相手: 情シス）
- `csvExport` … 一覧の CSV 出力（ブラウザに落とす）（聞く相手: 情シス）

**業務の言葉（この字で呼ぶ）**

| 業務の言葉 | 定義に書く名前 | この字で呼ばない |
| --- | --- | --- |
| 社員番号 | `employeeNo` | 社員コード / 従業員番号 |
| 所属部署 | `departmentCode` | 部門 / 課 |
| 在籍区分 | `employmentStatus` | ステータス |
| 取引先コード | `supplierCode` | 仕入先コード / ベンダーコード |
| 取引先区分 | `supplierType` | 種別 / タイプ |
| 与信限度額 | `creditLimit` | 与信枠 |
| 締め日 | `closingDay` | 締日 / 支払締め |
| 取引状態 | `tradeStatus` | 取引ステータス |

**業務ロジックの置き場**

- ログインして資格を確かめる … **枠組みの外（hatake は持たない）**。hatake は認証を持たない。画面は作れるが、確かめるのは API と認証基盤
- 誰がいつ何を直したかを残す（削除と一括は必ず。監査表に残す） … **枠組みの外（hatake は持たない）**（`auditLog`）。画面は押した結果しか知らない。残すのは API 側の責任
- 社員番号は採番しない（人事が決めた番号を手で入れる） … **サーバの担当**。採番するかしないかを決めるのはサーバ側。画面は入れさせるだけ
- 退職者をまとめて退職にする … **アプリ側に登録して足す**（`bulkRetire`）。一括の中身（何件ずつ・失敗したらどうするか）はアプリ側
- 与信限度額がいくらまで妥当か … **枠組みの外（hatake は持たない）**。購買部の別システムが正。ここでは記録するだけ
- 同じ1件を2人が同時に直したら、更新日時が変わっていたら弾いて読み直させる … **サーバの担当**。先に保存した人の入力が黙って消えるのを止める。マスタは直す人が少ないので楽観で足りる
- 一括の退職は1件ずつ確定し、失敗した行だけ残す … **サーバの担当**。全部取り消すと「40件目で落ちたら最初からやり直し」になる。人事は少しずつ直す
- 保存の検証は同じ定義でサーバでも回す … **サーバの担当**（`formValidator`）。画面の検証は親切であって守りではない（API を直接叩けば通る）
- 役割はログイン時にこのシステムが返す（admin / hr / viewer） … **枠組みの外（hatake は持たない）**。当面は自前の認証。AD に差し替えるときは、group をこの3つに写す
- 一括の退職を誰かに知らせるか → 知らせない（人事が画面で結果を見て終わり） … **枠組みの外（hatake は持たない）**。退職処理は人事の中だけで完結する。後工程に自動で流す先がいまは無い

> 「枠組みの外」「サーバの担当」と書いてあるものは、**画面側に実装しない**（画面には結果だけを出す）。判断そのものを Dart / TypeScript で書き始めない。

**名前の決めごと**

- 画面 id は `snake_case`
- 項目名は `camelCase`
- ボタン id は `camelCase`
- Repository キーは `camelCase`
- 役割名は `camelCase`
- `type: date` の項目は `Date` で終わらせる

**定義を書くとき**

- 書けたら `npx hatake advise <定義> --project definitions/hatake.project.yaml` にかける（上の名前と言葉の決めごととの食い違いが出る）
- **上の「業務の前提」は機械が見ていない**（読むのはあなた）。前提に反する定義を書いても、道具は何も言わない
