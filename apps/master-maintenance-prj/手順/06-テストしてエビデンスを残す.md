# 05. テストしてエビデンスを残す

**目的**: 「書ける」ではなく「**その値でどうなるか**」を確かめて、**納品できる形**で残す。

## 先に知っておくこと

**hatake にエビデンスを出す機能は無い。**

| 枠組みが持つもの | 持たないもの |
|---|---|
| `hatake run` … その値でどうなるか（検証・計算・押せるか） | **スクリーンショット** |
| `hatake run --cover` … まだ試していない分岐 | **API の実行記録** |
| `hatake run --widget-draft` … 画面の試験の下書き | **納品用の紙（ケース一覧・結果表）** |
| `hatake_test` … 画面を出して押す試験 | |

理由は認証と同じで、**エビデンスの様式は案件ごとに違う**から（客先の様式がある）。
だから `tests/` に自分で作る。この案件では:

```
tests/
├─ scenarios/*.json   値の台本（hatake run が読む）
├─ api/run.mjs        API を叩いて Markdown に落とす
└─ screen/shots.mjs   ブラウザで開いてスクショ＋Markdown に落とす
```

`hatake shot`（定義から画面の写真を撮る）は**ロードマップに載っているが未実装**。

---

## 人がやること

**何を確かめるかを決める。** 道具は「まだ試していない分岐」までは言えるが、
**業務として何を確かめるべきか**は言えない。

## AI に投げる（1）値のテスト

````
definitions/app.yaml の値のテストを作って。

1. まず hatake run --draft で下書きを起こす（TODO_ が入るので、業務として
   ありうる値に置き換えて）
2. 業務として確かめたいものを足す:
   - 社員番号が6桁でない / 英字が混ざる
   - 退職にすると退職日が必須になる
   - 退職日 < 入社日
   - 法人のときだけインボイス番号が必須（個人なら要らない）
   - 境界（退職日 = 入社日、与信限度額 = 0）
3. hatake run --cover を回して、**まだ試していない分岐が0件になるまで**足す
4. 名前の頭に項番（S-01…）を付ける。ケース一覧から辿れるように

**期待値は下書きのまま使わないで**（--draft は「いまの答え」を写しているだけなので、
業務として正しいかは私が見る）。
````

**必ず入れる:**

- **`--cover` を0件にする** ← これが「漏れが無い」の唯一の機械的な根拠
- **期待値を下書きのまま使わせない**（`--draft` は今の挙動を写すだけ。それを期待にすると
  「いまこう動いている」を確かめるだけの紙になる）
- **項番を付ける**（結果から辿れないエビデンスは使えない）

## AI に投げる（2）API のテスト＋実行記録

````
tests/api/run.mjs を作って。API を実際に叩いて、**納品用の Markdown** に落としたい。

確かめたいこと:
- ログイン（成功・失敗・未ログインで弾かれる）
- 定義に無い検索条件が無視される
- 役割で見えない列が**返ってこない**（viewer に内線）
- 役割で操作が止まる（hr は取引先を直せない）
- 一括の上限がサーバでも効く（hr は20件・admin は50件）
- 一括の部分失敗（失敗した行が名指しで返る）
- 同時更新で後から来た人が弾かれる

記録の形:
- 項番（A-01…）・確かめたいこと・期待・結果の表を先頭に
- 1件ごとに**投げたものと返ってきたものをそのまま**載せる（要約しない）
- **落ちても最後まで回して、落ちた件も記録に残す**
- 回す前にデータを初期状態に戻す（何度回しても同じ結果になるように）
````

**必ず入れる:**

| | なぜ |
|---|---|
| **やりとりをそのまま載せる** | 要約した記録は「本当にそう返ったか」を確かめられない＝エビデンスにならない |
| **落ちても最後まで回す** | 1件目で止まると、残りが「試していない」のか「通った」のか分からない |
| **落ちた件も残す** | 都合の悪い結果を落とすと、その紙全体が信用されなくなる |
| **データを戻してから回す** | 戻さないと2回目から結果が変わる（実際、一括の試験がそうなった） |

## AI に投げる（3）画面のスクリーンショット＋一覧

````
tests/screen/shots.mjs を作って。画面を実際に開いてスクショを撮り、
**項番つきの Markdown** に落としたい。

撮るもの（役割ごとの違いがこの案件の見どころ）:
- ログイン画面
- 社員マスタ（hr）… ボタンが全部出ている
- 取引先マスタ（hr）… 範囲と複数選択の検索。CSV 出力は出ない
- 部署マスタ（hr）
- 社員マスタ（viewer）… CSV・一括・選択欄が消える
- 取引先マスタ（admin）… CSV 出力が出る

決めごと:
- **Docker で回す**（手元に Chrome を入れさせない）
- 1400x900 で撮る
- **フォントが読み終わるまで待つ**（早く撮るとアイコンが豆腐になる）
- 撮ったものは消して撮り直す（前回の残りが混ざらないように）
- Markdown には項番・役割・**目で見て確かめること**・画像を並べる
- **スクショは証拠であって判定ではない**、と紙の頭に書く
````

**必ず入れる:**

- **「目で見て確かめること」を1件ずつ書く** ← これが無いとただの画像置き場になる
- **スクショを合否にしない**。見た目を機械で判定すると、余白が1px 動いただけで落ちる紙になる。
  合否は値（`hatake run`）と API が持つ
- **フォントを待つ**。アイコンが豆腐（□）の紙を客先に出すと「壊れている」に見える

## AI に投げる（4）ケース一覧

````
docs/4-テスト/ケース一覧.md を作って。

- S（値）・A（API）・G（画面）の3種類と、それぞれの結果ファイルへのリンク
- 項番ごとに「条件」と「期待」の表
- **確かめていないもの**の節を必ず入れる（紙に書いていないことは、やっていないのと同じ）
- 既知の見た目の問題があれば、それも書く

見栄えを良くするために、やっていないことを書かないで。
````

**いちばん大事なのが「確かめていないもの」の節。** 全部やったように見える紙は、
あとで「これは試していなかったのか」と揉める。

---

## 回す

```bash
docker compose up -d
bash tools/run-tests.sh          # 全部
bash tools/run-tests.sh scenarios # 値だけ（環境が要らない）
```

## 終わりの判定

| | |
|---|---|
| 値 | 全件が期待どおり・**`--cover` が0件** |
| API | 全件が期待どおり |
| 画面 | 全枚数が撮れている・**目で見て「確かめること」を満たしている** |

最後の1つだけは人がやる。そこは機械に代わってもらえない。

---

## 実際に起きたこと

作りながら3つ踏んだ。どれも**回してみないと出ない**もの:

| | |
|---|---|
| **2回目から結果が変わった** | 一括の試験が前回の続きから始まっていた。postgres の image はデータの置き場をボリュームとして宣言しているので、コンテナを作り直しても中身が残る（`--renew-anon-volumes` が要る） |
| **アイコンが豆腐（□）で写った** | `pubspec.yaml` に `uses-material-design: true` が無く、アイコンのフォントがそもそも同梱されていなかった |
| **定義を直したのに API が古いまま** | 定義を image に焼き込んでいた。compose でマウントして、直したら `restart` で効くようにした |
