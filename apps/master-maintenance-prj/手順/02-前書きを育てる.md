# 02. 前書きを育てる（人の仕事）

**目的**: 定義を書く**前に** AI に読ませる1枚を作る。

`definitions/hatake.project.yaml` … この案件は何か・誰が使うか・**できないこと**・
業務の言葉と項目名の対応・名前の決めごと。

## AI に投げる（下書きを起こす）

````
hatake project --draft --from docs/1-要件定義/案件の説明.md で下書きを起こして。

そのあと、メモに書いてある用語（社員番号・在籍区分・与信限度額…）を glossary に、
決めごとを logic に入れた形まで持っていって。
ただし**私が言っていないことは書かないで**。足りない所は「ここは決めていません」と
言ってくれれば、こちらで埋める。
````

→ `/前書き` でも同じ。

**「言っていないことは書かないで」は必ず入れる。** 前書きは案件のことを書く紙なので、
AI に想像で埋められると**それっぽいけど誰も決めていないこと**が設計書として残る。

## 人がやること

下書きは**ほとんど空で返ってくる**（資料の見出しから拾える所しか拾わない作りなので）。
そこから育てるのが人の仕事。

| 節 | 何を書くか | 機械が見るか |
|---|---|---|
| `system.what` / `users` | 何のシステムか・誰が使うか | 見ない |
| `system.premises` | **できないこと** | 見ない |
| `glossary` | 業務の言葉 → 定義に書く名前 | **見る** |
| `logic` | 業務ロジックの**置き場**（中身は書かない） | **見る** |
| `naming` | 名前の形 | **見る** |

## 終わりの判定

````
npx hatake project definitions/hatake.project.yaml --coverage definitions/*.yaml
````

## 実際に起きたこと（ここで2回やり直した）

**① 辞書の見出しを広く取りすぎた。**
`term: 区分` と書いたら「在籍区分」まで巻き込んで、助言が
「`employmentStatus` に supplier が入っていません」と言い出した。
→ 見出しを `取引先区分` に変えた。**glossary は部分一致で効く。**

**② 守れない決めごとを書いた。**
`naming.suffix.number: Amount` と書いたら、`creditLimit` を `creditLimitAmount` に
しろと鳴り続けた。業務の言葉から離れるのでやめた。
→ **守れない決めごとを書くと助言が鳴りっぱなしになり、そのうち誰も読まなくなる。**
