# 機能網羅（AI 向けの指示）

**この案件は業務のふりをしません。** 目的は2つだけ:

1. DSL のキーを**一度ずつ全部書いて動かす**（1.0 で凍らせる前に）
2. 版を上げたときの**差分を1か所で見る**（移行確認）

## 守ること

1. **キーを足したら、この定義にも書く。**
   `node tool/check-coverage.mjs --check`（フレームワーク側）が**0件**になるまで。
   書けないものは `spec/coverage-exclusions.json` に**理由つきで**書く。

2. **画面は「確かめたいこと」で分ける。** 業務で分けない。
   落ちたときにどの画面かで原因が分かるようにするため。

3. **業務ロジックを足さない。** API は決め打ちの値を返すモック。
   業務らしさが要る見本は別に2本ある。

4. **出力は全部 `--check` を持つ。**
   `build-design-docs.mjs` / `refresh-docs.sh` / `run-tests.sh`。
   版を上げたときに**差分が出ない**なら、それは確認になっていない。

5. **撮った絵は目で見る。** この案件の不具合2件のうち1件は、
   スクリーンショットを見るまで誰も気づかなかった（テストは全部通っていた）。

## 触っていいもの / いけないもの

| | |
|---|---|
| ✅ `definitions/app.yaml` | 網羅のために足す |
| ✅ `node-src/` `flutter-src/` | 定義が要求しているものを足す |
| ⚠️ `definitions/hatake.project.yaml` | 人が決めたことだけ |
| 🚫 `docs/**/出力-*.txt` `docs/2-設計/**` | 生成物。道具で作り直す |

## この案件だけの注意

- **認証を持たない。** 役割は URL の `?role=tester,admin`
- **DB を持たない。** `POST /api/reset` で初期状態に戻る（証跡を撮る前に叩く）
- **`type: detail` をメニューに置かない。** 鍵を渡す場所が無いので必ず空になる
  （0.9.12 から `detail-page-in-menu` が言う）

## 版

`../../hatake.version` の tag に pin。**上げるのは人の判断**で、
上げたら上の `--check` を3つとも回して差分を見る。

## この案件について

> ここは `definitions/hatake.project.yaml` から生成した節です（`npx hatake project --agents`）。
> **直すときは前書きを直して貼り直す**（同じことを2か所に書くと必ず食い違う）。

hatake の DSL で書けることを**一度ずつ全部書いて、実際に動かす**ためのアプリ。 業務のふりはしない。画面は業務ではなく「確かめたいこと」で分けてある。

**使う人**

- 試す人（tester）。全画面を触る
- 管理（admin）。持ち出しと、区切りの大きいほうを触る

**業務の前提（できないことも含む）**

- 業務ロジックは持たない。API は決め打ちの値を返すだけのモック。
- 保存しても残らない（毎回同じ状態から始まる＝証跡が撮り直せる）。
- 認証は持たない。役割は URL の `?role=` で切り替える（**見本のための割り切り**）。
- 納品物の見本ではない。人に見せる設計書としての値打ちは狙わない。

**外の相手**

- `itemRepository` … 網羅用の1件（この案件のモック API）（聞く相手: この見本）
- `lineRepository` … 明細（帳票が読む）（聞く相手: この見本）
- `groupRepository` … 親の選択肢（聞く相手: この見本）
- `childRepository` … 子の選択肢（親で絞る）（聞く相手: この見本）

**業務の言葉（この字で呼ぶ）**

| 業務の言葉 | 定義に書く名前 | この字で呼ばない |
| --- | --- | --- |
| コード | `itemCode` | ID |
| グループ | `groupCode` | 分類 |

**業務ロジックの置き場**

- 保存しても残らない（モックなので） … **サーバの担当**。証跡を何度でも撮り直せるようにするため
- 採番しない。コードは手で入れる … **サーバの担当**。網羅が目的なので、番号の規則は持たない
- 同時更新は見ない（1人で触る前提） … **サーバの担当**。モックなので衝突が起きない
- 一括は1件ずつ確定し、失敗した行だけ残す … **サーバの担当**。区切って実行する所を確かめるため、途中で失敗する行を用意してある
- 保存の検証はサーバでも回す … **サーバの担当**（`formValidator`）。画面の検証は親切であって守りではない
- 役割で隠したものは API でも止める … **枠組みの外（hatake は持たない）**（`authz`）。画面の roles は見せ方だけ
- 役割は URL の `?role=` で配る（見本のための割り切り） … **枠組みの外（hatake は持たない）**。認証を持たないため
- 端数は扱わない（金額は整数で持つ） … **枠組みの外（hatake は持たない）**。丸めの確認は2本目（受注入力）でやってある
- 監査は残さない … **枠組みの外（hatake は持たない）**。モックなので
- 誰にも知らせない … **枠組みの外（hatake は持たない）**。モックなので
- 種別（standard / special / trial）は画面のボタンでは変えない。モックが返す値のまま … **枠組みの外（hatake は持たない）**。網羅が目的なので、状態を進める道筋は持たない（枠組みもワークフローを持たない）
- 帳票は刷った時点の値を読む … **枠組みの外（hatake は持たない）**。モックなので常に同じ値

> 「枠組みの外」「サーバの担当」と書いてあるものは、**画面側に実装しない**（画面には結果だけを出す）。判断そのものを Dart / TypeScript で書き始めない。

**名前の決めごと**

- 画面 id は `snake_case`
- 項目名は `camelCase`
- ボタン id は `camelCase`
- Repository キーは `camelCase`
- 役割名は `camelCase`
- ステップ id は `camelCase`
- カード id は `camelCase`

**定義を書くとき**

- 書けたら `npx hatake advise <定義> --project definitions/hatake.project.yaml` にかける（上の名前と言葉の決めごととの食い違いが出る）
- **上の「業務の前提」は機械が見ていない**（読むのはあなた）。前提に反する定義を書いても、道具は何も言わない
