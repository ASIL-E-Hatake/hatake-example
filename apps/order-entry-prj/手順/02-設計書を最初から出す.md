# 02. 設計書を最初から出す

**目的**: 納品する設計資料を、**定義ができた直後**に出す。あとから頼まない。

## 1本目の反省

1本目は「テストの記録」を先に指定してしまい、設計資料を**後から**頼みました。
後から頼むと、

- その間に定義が進んでいて、資料と食い違う
- 「何を出すか」を後から決めることになる（客先の様式に合わせられない）

2本目は、定義が `hatake check` で警告ゼロになった**その場で**出しています。

## AI に投げる

````
定義が警告ゼロになったので、納品する設計資料を出して。

出すもの（全部 definitions/app.yaml から生成。手で書かない）:
- 画面一覧
- 画面遷移図（Mermaid ＋ SVG）
- 画面設計書（画面ごとに1枚。**DSL のキー名を出さない**。読む人は YAML を知らない）
- API 一覧（画面が要求している口）
- 権限マトリクス

道具はリポジトリ直下の tools/build-design-docs.mjs を使って、
案件ごとに違う所（API の実装がどこか・定義に書けない口は何か）は
tools/design.config.json に書いて。

生成物には「これは生成物です・手で直さない・作り直し方」を必ず頭に付けて。
そのあと --check が通ることも確かめて。
````

## 必ず入れる3つ

| | なぜ |
|---|---|
| **定義から生成する** | 手で書いた設計書は3か月で嘘になる。生成なら `--check` で古さが見える |
| **DSL のキー名を出さない** | 読むのは業務の人。`visibleWhen` と書いてあっても意味が分からない |
| **「生成物です」と書かせる** | 書いていないと、誰かが手で直して、次の生成で消える |

## 出てくるもの

[docs/2-設計/](../docs/2-設計/) の7枚です。定義を直したら

```bash
node tools/build-design-docs.mjs
```

で作り直すだけ。CI では `--check` を回して、古いまま commit されるのを止めます。
