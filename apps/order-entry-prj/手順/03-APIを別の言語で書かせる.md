# 03. API を別の言語で書かせる（この案件は Java）

**目的**: 画面（Flutter）とサーバ（Java）が**同じ定義1枚**を読む形にする。

## AI に投げる

````
この案件の API は Java（Spring Boot）で書いて。

要点:
- 画面と**同じ definitions/app.yaml** を読む。API 側にコピーを持たない
- 検索できる条件は定義から（QueryBuilder）。書いていない項目では絞らせない
- 保存の検証は定義から（FormValidator）。画面とまったく同じ規則を通す
- 列の roles はサーバでも効かせる（画面で隠すだけでは API から取れてしまう）
- 一括の上限も定義から（BulkLimits）

hatake は git の tag から入れて（JitPack）。pin する tag は hatake.version を見て。

返す形は hatake_http の契約に合わせて:
  GET <collection>       → {items, totalCount}
  POST <collection>      → 作ったレコード
  GET/PUT <collection>/{key} / DELETE → 204
````

## 踏んだこと（2本目で実際に）

| | 何が起きたか | どうしたか |
|---|---|---|
| **枠組みの穴** | Java 版は app 定義の画面を**中身まで読めなかった**（`form` が取れない） | 枠組みに `AppParser.parseAppPagesYaml` を入れてもらった |
| **枠組みの穴** | Java 版が列の `roles` を落としていた | 枠組みに `ColumnDefinition.roles` を入れてもらった |
| **型** | 範囲検索が 500（問い合わせの値は全部「文字」で届く） | 定義の `filters[].type` から `?::numeric` / `?::date` を付けた |

上2つは**外から使わないと出ない**種類でした。tag を切り直して（v0.9.1）から先に進んでいます。

> **穴が出たときの進め方**: 見本の中に回避コードを書くのではなく、
> **枠組みを直して tag を切り直す**。回避コードを残すと、それが見本の「正しい書き方」に
> 見えてしまいます（1度 `HatakeGap.java` という穴埋めを書きましたが、消しました）。

## 確かめ方

````
API ができたら、定義に書いた規則が**サーバでも効いている**ことを確かめる
テストを書いて。画面を通さず API を直接叩く形で。

特に見たいもの:
- 画面と同じ検証（必須・桁・項目間・行の中・行をまたぐ）
- 役割で列が落ちること
- 一括の上限が定義の数と同じであること
- 採番・締め・同時更新・部分失敗（どれも定義に書けない＝サーバの担当）
````
