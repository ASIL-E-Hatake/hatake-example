# この案件を通してみた記録（導入を検討する方へ）— 2本目

hatake ＋ AI で受注入力システムを作り、**同じものを hatake 無しでもう一度作って
比べました**。

**5分で知りたい方はこのページだけで足ります。**

## やってみた案件

受注入力（営業事務が電話・FAX で受けた注文を入れて、出荷指示まで出す）。

| | |
|---|---|
| 画面 | 5枚（照会・**ウィザード入力**・詳細・ダッシュボード・**帳票**） |
| 役割 | 3種（営業 / 営業事務 / 管理者）で見え方が変わる |
| 業務の作り | 親子明細・**軽減税率の混ざる消費税**・採番・締め・同時更新・一括の部分失敗・監査 |
| 構成 | 画面（Flutter Web）＋ API（**Java / Spring Boot**）＋ DB（PostgreSQL） |

**動きます。** `docker compose up` だけ（Flutter SDK も JDK も要りません）。
→ [案件の README](../../README.md)

### 予想が外れた所を、外れたと書きます

**「AI が書く量が 1/4 になる」は、サーバ側については成り立ちませんでした。**
差は15行です。1本目のまとめは見積もりでそう書いていたので、訂正します。

両方でまったく同じファイルが8枚あります（認証・監査・DB・出荷連携・マスタ照会）。
**もともと枠組みの外**と宣言してある所なので、1行も減りません。

**差が出たのは画面側**で、hatake 版の画面 399 行には**画面を組むコードが1行も
ありません**。

## 行数より大きい差が3つ

### ① 同じ規則を2か所に書くことになる

無し版では、まったく同じ規則が Java と Dart の両方にあります ── 必須・桁・
納期の前後・商品の重複・**税率ごとの丸め**・列の出し分け・一括の上限と文言。

**片方だけ直しても、誰も何も言いません。** 画面から消えたのに API では取れる
（またはその逆）になり、気づくのは使う人です。

### ② 設計書が出ない

hatake 版の[設計資料7枚](../2-設計/)は**全部生成物**です。定義を直したら作り直す
だけなので腐らず、`--check` で CI が古さを見ます。無し版には定義が無いので、
**同じ紙を出す口がありません**。

### ③ 道具が検算してくれない

この案件だけで道具が止めたもの: 紙に収まらない列幅・一度も効かない上限・
呼ばないことにした言葉・**人が決めないと決まらないこと11件**。

## 課題

**サーバだけの案件には効きません**（実測で引き分け）。1〜2画面で終わる案件も、
画面そのものが要件の案件も向いていません。分かれ目はだいたい3画面です。

`hatake run`（値のテスト）は**アプリが足した計算を回せない**ので、消費税だけは
API テストで確かめています（道具はそう言ってくれます）。
