# 変更に強いか（2本目・**実測**）

> **この紙の問い**: 作ったあとに業務が変わったとき、hatake 有りと無しでどれだけ手間が
> 違うか。[工数の比較](工数の比較.md)は「作るとき」を測って、**行数はほぼ引き分け**
> （置き場所が変わっただけ）だった。hatake の値打ちを数字で言えるとしたら、作ったあと
> ＝**変えるとき**のはず。それを確かめる。

---

## 1. 先に決めたこと（手を付ける前に書いた）

**両方とも作ったのは同じ AI（このリポジトリの作り手）**で、どちらにも肩入れできる立場に
いる。だから**変更の中身と測り方を、手を付ける前にこの節に書いて固定した**。あとから
「hatake に有利な変更」を選べないようにするため（この節は、結果を書くときに直していない）。

### 変更（業務でよく来る3種類から1つずつ）

| # | 種類 | 中身 |
|---|---|---|
| ① | **項目を足す** | 受注に「客先注文番号」（`customerOrderNo`、任意・20文字まで）。入力画面で入れて、DB に残し、受注照会の**列**と**絞り込み（前方一致）**、**CSV**、**受注詳細**、**注文請書**に出す |
| ② | **規則を変える** | 「納期は受注日**以降**」→「納期は受注日の**翌日以降**」（当日納品をやめる）。画面でもサーバでも止める |
| ③ | **権限を変える** | 受注の取消（一括・1件とも）を、営業事務に加えて**管理者にも**許す |

そのほかに**前提合わせ（⓪）**を1つ。0.9.23 で「管理者も受注を入力できる」を API 試験
（A-29）に足したが、無し版は入れる人を `sales` / `clerk` と決め打ちしたままで、**いま
A-29 に落ちる**。①〜③と混ぜると数字が読めなくなるので、別に測って別に書く。

### 測るもの

| | 測り方 |
|---|---|
| 触ったファイル | 変更の前後で写しを取り、差分で数える（版ごと・共用ごとに分ける） |
| 変えた行 | 差分の足した行＋消した行。**空行とコメントの行は数えない**（[工数の比較](工数の比較.md)と同じ規則。hatake 版はコメントが多いので、入れると hatake が不利になる） |
| 設計書 | hatake 版は道具で作り直す（手で直した行には数えない）。無し版は設計書が無い＝**直す紙が無い**ことも結果として書く |
| 試験 | API 試験（`tests/api/run.mjs`）は**両方に同じものを1文字も変えずに**通す。足す試験も1回書いて両方に通す |
| 道具が見つけたこと | 書き間違い・書き漏れを道具が言ったか（言ったなら何を） |

**測らないもの**: 作業時間と AI の往復数。同じ AI が2回やるので、2回目は1回目で考えた
ことを知っている（条件がそろわない）。代わりに「**どこを直す必要があったか**」を全部
並べる（数より、漏らしたら何が起きるかのほうが読み手に効く）。

### 共用のもの（どちらの版にも数えない）

DB のスキーマと種データ（`docker/postgres/`）と API 試験は2つの版で同じファイルを使う。
ここを触った分は「共用」として別に書く。

---

## 2. 結果

（ここから下は変更を入れたあとに書いた）

### 2-1. 数字（空行とコメントを除いた、足した行＋消した行）

**定義とコード**（試験・生成物・共用は除く）:

| 変更 | hatake 版 | 無し版 |
|---|---|---|
| ⓪ 管理者も入力できる（前提合わせ） | 0（0.9.23 で定義の `roles` 1行として入っている） | 1 ファイル・4 行 |
| ① 項目を足す | 4 ファイル・25 行 | **8 ファイル・46 行** |
| ② 規則を変える | **1 ファイル・2 行**（定義の `operator` と文言） | 2 ファイル・4 行 |
| ③ 権限を変える | **1 ファイル・2 行**（定義の `roles`）＋前書き 2 行（役割の説明の書き換え） | 3 ファイル・6 行 |
| **①〜③の計** | **31 行**（のべ 7 ファイル） | **56 行**（のべ 13 ファイル） |

それ以外（どちらの版にも数えていないもの）:

| | |
|---|---|
| 共用 | DB のスキーマ 3 行（①）、API 試験 83 行（①〜③で6件足した＝A-30〜A-35。ほかに A-20 の説明の文） |
| hatake 版の試験 | シナリオ 8 行（②。`hatake run` の S-04 / S-05）、画面試験の期待の文 1 行（①） |
| hatake 版の生成物 | 設計書・出力紙・`CLAUDE.md` の印の中、のべ 13 ファイル・45 行。**全部道具が作り直した**（手で直した行は 0） |
| 無し版の生成物 | **無い**（設計書を持っていない＝直す紙が無い。持っていたら手で直すことになる） |
| 手書きの文書 | 要件のメモ 1 行（②。業務の決めごとが変わったので） |

試験は**毎回両方に同じものを通した**。最後は hatake 版 35 / 35、無し版 34 / 35（落ちたのは
A-28「画面の定義を配っている」＝無し版には定義が無いので、前から落ちる。⓪の前は A-29 も
落ちていた）。値の試験（`hatake run`）15 / 15、画面は両方撮り直した。

### 2-2. 行の数より効いたこと: **同じことを何か所に書いたか**

行数は ①〜③ で **31 対 56＝無し版が約1.8倍**。作るときの比較（合計 1.8倍）とほぼ同じで、
これだけなら「変えるときも同じくらい」としか言えない。差が出たのは**書いた場所の数**:

| 変更 | hatake 版 | 無し版 |
|---|---|---|
| ① 項目を足す | 定義の5か所（入力欄・絞り込み・列・詳細・紙）＋サーバの書く SQL の4か所 | **23か所**（入力画面6・規則3・照会5・詳細1・紙1・DTO 1・書く SQL 4・検索の白名簿2） |
| ② 規則を変える | **1か所**（画面もサーバもその1行を読む） | **2か所**（Java の `CrossFieldRules` と Dart の `rules.dart`） |
| ③ 権限を変える | **1か所**（メニュー・ボタン・一括の口・1件の口が全部その1行を読む） | **3か所**（一括の口・1件の口・画面のボタン） |

②と③で無し版が書いた場所は、**どれか1つを忘れても動く**:

- ② の Dart 側だけ忘れる → 画面では当日が通るのに、保存で 400（逆なら API を叩けば当日が通る）
- ③ の画面だけ忘れる → 管理者にボタンが出ない（誰も困らないので気づかない）。1件の口だけ
  忘れる → 一括では消せるのに、1件ずつだと 403

hatake 版は**忘れる場所が無い**（1か所しか無い）。行数の差は小さいが、**漏らしたときに黙る
場所の数**は 1 対 2〜3 になる。この見本の試験は今回それを全部押さえる形で足した（A-33〜A-35）が、
試験を足さなければ、無し版の漏れは画面を押すまで分からない。

### 2-3. hatake 版が負けた所

- **注文請書に「客先注文番号」を見出しで出せなかった。** 帳票の定義には、紙の見出し（受注番号の
  横）に項目を添える口が無い（ロードマップ「帳票の見出し項目」）。`groupBy` を1段足すと小計が
  2つ出るので、**列で出した**。紙の幅は増やせないので商品名を 70pt 詰めた結果、紙の上で
  「客先注…」「A4コピー用…」と**切れて出る**（[G-04](../4-テスト/画面/G-04-注文請書-clerk.png)）。
  無し版は見出しの字に1行足しただけで、きれいに出た（[N-04](../../no-framework/画面/N-04-注文請書-clerk.png)）。
- **項目を足すとき、サーバの書く SQL は hatake 版でも手で直した**（insert と update の4か所）。
  枠組みは DB を持たない（持たないと決めている）ので、ここは減らない。①の hatake 版 25 行の
  うち 15 行はサーバ（Java）。
- **道具が要らないことを言った。** 「客先注文番号」を用語辞書に足したのに、`check` が
  「『客先』は『取引先』と呼びます」「『注文番号』は『受注番号』と呼びます」と2件の助言を
  出した（避ける言葉を含むが、それ自体が辞書に載っている言葉）。枠組みの側に返す。

### 2-4. 変えて初めて見つかったもの

- **hatake 版のサーバの `Sql.java` に、前方一致（`startsWith`）が無かった。** 定義に
  `operator: startsWith` と書くと、枠組みの `QueryBuilder` はそのとおり渡してくるのに、こちらの
  SQL に組む所が知らずに**完全一致**にしていた（黙って0件）。無し版の検索の白名簿にも前方一致が
  無かったので、条件は同じ（どちらも足した）。A-31 が押さえている。
- **無し版は、入れる人の決め打ちが残っていた**（⓪）。0.9.23 で足した試験（A-29）に落ちていた。
  hatake 版は 0.9.23 で「入れる人は定義の画面の `roles`」に寄せたので、要件の「管理者は全部」と
  ずれなかった。③も同じ形で、要件では管理者は「全部」なのに、両方の版とも取消を営業事務だけに
  していた（定義と要件の食い違い）。

### 2-5. まとめ

| | |
|---|---|
| **行数** | 変えるときも約 1.8 倍（作るときと同じ）。**行数では大差はつかない** |
| **書く場所** | 規則と権限は **1 か所 対 2〜3 か所**。項目は **約 10 か所 対 23 か所** |
| **漏れたとき** | hatake 版は漏らす場所が無い。無し版は**黙って片方だけ古い**状態になりうる |
| **設計書** | hatake 版は道具が作り直す（13 ファイル）。無し版は**そもそも無い** |
| **負けた所** | 帳票の見出しに項目を出せない（列で代用して紙が窮屈になった） |

**変更に強い、と言える根拠は「行が減る」ではなく「同じことを1か所にしか書かない」**だった。
作るときの比較で「置き場所が変わっただけ」と書いた行は、**変えるときに直す場所の数**として
効いてくる。
