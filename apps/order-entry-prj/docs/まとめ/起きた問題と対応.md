## フレームワーク本体（4件）

### F-1 `optionsFrom` に Repository を書いても、黙って効かない

**いちばん重い1件。** 選択肢を Repository から引くキーは `optionsSource` なのに、
`optionsFrom`（＝連動する親の項目名を書く所）に Repository を書いていました。

- **検証は exit 0**。画面も出る。**選択肢だけが空**
- しかも生成した設計書まで「選択」としか書かれず、**静かに嘘をついていた**
- キー名は正しいので、目で読んでも気づけない

1本目にも入っていました（所属部署・上位部署の3か所が、空のドロップダウンのまま
動いていた）。

**対応**: 枠組みに警告 `key-wrong-shape` を追加（0.9.1）。形が一意に決まるキーに
形の違う値を書いたら言う。見るのは**形が一意に決まるキーだけ**
（`filters` はカードでは入れ子・検索では並びなので見ない）。

### F-2 Java 版が app 定義の画面を中身まで読めない

`AppParser.parseAppYaml` が返すのは `PageRef`（id・種別・タイトル・Repository）だけで、
**`form` も `search` も取れない**。「画面と同じ定義でサーバでも検証する」という
この枠組みの主張が、**Java 版だけ通らない**状態でした（Dart 版と TS 版には在った）。

**対応**: `AppParser.parseAppPagesYaml` を追加（0.9.1）。

### F-3 Java 版が列の `roles` を落としていた

「描画専用のキーは持たない」として落としていましたが、列の `roles` が決めるのは
**誰がそのデータを見てよいか**。画面で隠すだけなら API を直接叩けば取れます。

**対応**: `ColumnDefinition.roles` を追加（0.9.1）。

### F-4 ダッシュボードと帳票では、一覧のコードが名前にならない

0.9.1 で crud / search は直っていましたが、**ダッシュボードのカードと帳票の明細**は
そのままで、`draft` / `confirmed` / `cancelled` が並んでいました。
紙のほうが深刻で、`confirmed` と刷られた注文請書は取引先に送れません。

**どうやって気づいたか**: **スクリーンショットを目で見て**。
API テスト28件も `hatake run` 15件も、この件は1つも落としていません。

**対応**: 枠組みを直して（0.9.2）、PDF を組む側（`hatake_print`）も同じにした。

> **直しただけでは出ませんでした。** ダッシュボードには入力欄が無いので、
> 名前を引ける相手は**出力条件に書いてある選択肢**だけ。この案件のダッシュボードは
> 条件が「受注日」しか無かったので、受注状態の条件を足して初めて名前になりました。
> 枠組みは**勝手に名前を作らない**（引ける相手が無ければ値をそのまま出す）ので、
> これは設計どおりです。

## 書き間違い — 証跡を見て気づいたもの（3件）

**テストは全部通っていました。** 絵を見るまで誰も気づきません。

| 何が出ていたか | 本当は |
|---|---|
| 税率が `0.10%` | `percent` の既定は「もう百分率の数」。割合で持つなら `config: { ratio: true, decimals: 0 }` |
| 一覧の右端（入力者・行のボタン）が切れていた | 列幅の合計が画面より広かった |
| **ダッシュボードのつもりで帳票が写っていた** | スクリーンショットのメニュー座標が1段ずれていた |

3つ目がいちばん怖い種類です。**「ダッシュボード」という名前の画像ファイルに
帳票が写ったまま納品される**ところでした。撮った絵を目で見ないと分かりません。

## 環境まわり（3件）

| | 対応 |
|---|---|
| 範囲検索が 500（`bigint` と `text` は比べられない） | 定義の `filters[].type` から `?::numeric` / `?::date` を付けた。「数字に見えたら数にする」と当てにいくと `0001` のようなコードを壊す |
| JitPack の座標が分かりにくい | `com.github.<持ち主>:<リポジトリ>:<tag>`。`group` でも `artifactId` でもなく**git の持ち主とリポジトリ名**になる |
| 自分の検証が CI より甘かった | `dart analyze --no-fatal-warnings` を使っていて warning を見ていなかった。**CI と同じコマンドを使う** |

最後の1つは自分の手順の問題です。旗を足して検証を緩めると、落ちるのは CI になります。

## 枠組みの穴が出たときの進め方

1度、見本の中に回避コード（`HatakeGap.java`）を書きました。**消しました。**

回避コードを残すと、それが見本の「正しい書き方」に見えてしまいます。
見本は**配ったものを外から普通に使う**姿でないと意味がないので、

```
枠組みを直す → tag を切り直す → 見本をその tag に上げる → 証跡を撮り直す
```

という順で進めました（v0.9.1 と v0.9.2 の2回）。
