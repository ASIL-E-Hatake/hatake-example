## 1. 枠組みが持たないもの（自分で書くことになる）

2本目でアプリ側に書いたのは **約1,500行**（Java 1,148 ＋ Dart 399 のうち、
枠組みが持たない所）。内訳:

| | 何を書いたか | 使い回せるか |
|---|---|---|
| 認証・トークン | ログイン画面・署名つきトークン・毎回のヘッダ | ○ 案件をまたいで同じ |
| 本当の権限遮断 | 役割で止める・列を落とす | ○ 形は同じ |
| 監査 | 誰が・いつ・何をしたか | ○ 同じ |
| 同時更新の判定 | 更新日時で弾く | ○ 同じ |
| 採番・締め | 受注番号・締めた月の判定 | △ 案件ごとに規則が違う |
| 一括の中身 | 1件ずつ確定して失敗した行を返す | ○ 形は同じ |
| 外部連携 | 出荷指示を投げる | ✗ 相手ごと |
| DB への当て方 | SQL・型のキャスト・行のマップ | △ 形は同じ |

**1本目とほぼ同じ顔ぶれ**でした。使い回せるものが多いので、3本目はもっと速いはずです。

## 2. 定義に書けなくて困ったこと（2本目で新しく出たもの）

### 丸めが書けない

`computed` に丸めがありません。この案件は**軽減税率が混ざる**ので、
「税率ごとに畳んで、税率ごとに1回だけ切り捨てる」が要りました。

対応: `op` は開いた文字列なので、アプリが `tax` を登録して、中身は枠組みの
`computeInvoice`（適格請求書の数え方・3版同出力）を呼ぶだけにしました。

**これは設計どおり**です（丸めは業務の決めごとなので枠組みは持たない）が、
**代償が1つ**あります:

> `hatake run`（値のテスト）は**アプリが足した計算を回せません**。
> 道具はそう言ってくれます（「`op: tax` は登録が要ります。値は出しません」）が、
> **消費税の計算だけは値のテストで確かめられない**ということです。
> この案件では API テストで確かめました（10%分 632 ＋ 8%分 336 = 968）。

### 明細の行数に上限を掛けられない

「明細は1〜20行くらい」という要件でしたが、`required` で「1行以上」は言えても
「20行まで」は書けません（`maxRows` は一括のボタン用）。この案件では上限を
掛けていません。

### 行の項目でないものは畳めない

`join` で商品**名**を並べようとしましたが、商品名は一覧の列であって行の入力項目では
ないので、入力中のレコードには入っていません。商品**コード**を並べる形にしました。

## 3. 道具の側で気になったこと

### 生成した設計書が静かに嘘をつくことがある

`optionsFrom` の書き間違い（[起きた問題](起きた問題と対応.md) F-1）のとき、
画面設計書には「上位部署 … 選択」と書かれていました。**選択肢がどこから来るかが
書かれていない**のが正しい出力だったのですが、読む人には区別が付きません。

警告 `key-wrong-shape` を入れたので同じ事故は止まりますが、
**生成物は「書いてあることの言い直し」なので、元が間違っていれば間違ったまま出ます**。

### 証跡を人が見ないと分からない種類がある

2本目で見つけた不具合4件のうち、**1件はスクリーンショットを目で見て**見つけました
（ダッシュボードのコード表示）。API テスト28件も値のテスト15件も、1つも落としていません。

**テストが全部緑でも、絵は見てください。**
