# 受注入力（AI 向けの指示）

このフォルダで作業するときに最初に読む紙。

## この案件の作り方

**画面は定義（YAML）で作る。Flutter のウィジェットを手で書かない。**

- 定義: `definitions/app.yaml`（画面5枚）
- 前書き: `definitions/hatake.project.yaml` … **定義を書く前に必ず読む**
- 手順: `手順/` … 人が何を投げたか。同じ形で続ける
- 工程ごとの成果物: `docs/`

道具は `npx hatake <コマンド>`。仕様書は読まなくていい（**引ける**ようになっている）:

| 迷ったら | 引くもの |
|---|---|
| このキーはどこに書く？型は？ | `npx hatake reference <キー名>` |
| こういう画面の例は？ | `npx hatake examples <やりたいこと>` |
| この警告は何？ | `npx hatake rules <規則名>` |
| これは hatake で書ける？ | `npx hatake where <やりたいこと>` |

## 守ること

1. **定義を書いたら必ず `check` を通す。**
   ```bash
   npx hatake check definitions/app.yaml --project definitions/hatake.project.yaml
   ```
   事実（警告）が0件になるまで直す。**助言（好み）は勝手に当てない**（人に聞く）。

2. **前書きに書いていないことを定義に足さない。**

3. **`hatake ask` が返した問いに勝手に答えない。** 業務の判断なので人が決める。

4. **枠組みの外のものを画面に実装しない。**
   認証・採番・締め・監査・出荷連携は外に置いた。画面に出すのは**結果だけ**。

5. **生成物を手で直さない。**
   - `docs/**/出力-*.txt` → `bash tools/run-tests.sh` / `bash tools/refresh-docs.sh`
   - `docs/2-設計/**` → `node tools/build-design-docs.mjs`

6. **定義を直したら3つとも回す**（設計資料・出力紙・テスト）。

7. **道具そのものを案件の中に書かない。** リポジトリ直下の `tools/` に在る。
   案件側に置くのは設定だけ（`tools/design.config.json` / `tools/test.config.sh`）。

8. **証跡は撮ったら目で見る。** テストが全部緑でも、絵を見ないと分からない種類がある
   （2本目はそれで不具合を1件見つけた）。

## この案件だけの注意

- **消費税は `op: tax`**（アプリが登録した計算）。軽減税率が混ざるので、
  税率ごとに畳んで**税率ごとに1回だけ**切り捨てる。中身は枠組みの `computeInvoice`。
  → `hatake run` では値が出ない（道具がそう言う）。API テストで確かめる
- **単価と税率は商品マスタが正**。画面が送ってきた値は信じず、サーバが当て直す
- **API は Java**（Spring Boot）。hatake は JitPack から入る
  （座標は `com.github.<持ち主>:<リポジトリ>:<tag>`）

## この案件について

> ここは `definitions/hatake.project.yaml` から生成した節です（`npx hatake project --agents`）。
> **直すときは前書きを直して貼り直す**（同じことを2か所に書くと必ず食い違う）。

営業事務が電話・FAX で受けた注文を入れて、出荷指示まで出す画面。いまは Excel の 注文書を手で転記していて、単価の入れ間違いと消費税の計算違いが毎月出ている。

**使う人**

- 営業（sales・10人）。自分の拠点の受注を入れる・直す
- 営業事務（clerk・4人）。全拠点の受注を入れる・直す・取り消す
- 管理者（manager・1人）。ダッシュボードと帳票も見る

**業務の前提（できないことも含む）**

- ログインは hatake の外。社内ポータルの ID を使い、役割もそちらが返す。
- 受注番号は画面で入れさせない。**サーバが採番する**。
- 出荷指示は基幹システムの担当。こちらからは投げるだけで、結果は持たない。
- 単価は商品マスタの定価を使う。取引先ごとの契約単価は**今回やらない**。
- 締めた月の受注は直せない。締めの判断はサーバが持つ（画面は結果だけを見せる）。
- 取り消した受注は消さない。状態を「取消」にするだけ。
- 明細の金額・小計・消費税・合計は**画面が計算する**が、保存する値の正はサーバ。

**外の相手**

- `orderRepository` … 受注（ヘッダ）。この案件の API（聞く相手: 情報システム）
- `orderLineRepository` … 受注明細。この案件の API（明細を別に持つ）（聞く相手: 情報システム）
- `customerRepository` … 取引先マスタ（照会だけ）（聞く相手: 営業管理）
- `productRepository` … 商品マスタ（照会だけ。単価の出どころ）（聞く相手: 購買部）
- `shipmentGateway` … 出荷指示の連携先（基幹システム）（聞く相手: 基幹システム）

**業務の言葉（この字で呼ぶ）**

| 業務の言葉 | 定義に書く名前 | この字で呼ばない |
| --- | --- | --- |
| 受注番号 | `orderNo` | 注文番号 / オーダー番号 |
| 取引先 | `customerCode` | 得意先 / 客先 |
| 受注日 | `orderDate` | 注文日 |
| 納期 | `dueDate` | 納入日 / 希望日 |
| 受注状態 | `orderStatus` | ステータス |
| 商品 | `productCode` | 品目 / アイテム |
| 数量 | `quantity` | 個数 / 数 |
| 単価 | `unitPrice` | 価格 |
| 金額 | `amount` | 小計金額 |
| 小計 | `subtotalAmount` | 税抜合計 |
| 消費税 | `taxAmount` | 税額 |
| 合計 | `totalAmount` | 税込合計 / 総額 |

**業務ロジックの置き場**

- ログインして資格を確かめる・役割を配る … **枠組みの外（hatake は持たない）**。hatake は認証を持たない。社内ポータルが ID と役割を返す
- 受注番号を採番する … **サーバの担当**。連番の在り処はサーバ。画面では入れさせない
- 出荷指示を基幹システムへ投げる … **枠組みの外（hatake は持たない）**（`shipmentGateway`）。相手のシステムの担当。こちらは投げるだけで結果を持たない
- 締めた月かどうかの判断 … **サーバの担当**。締めの在り処はサーバ。画面は「直せない」という結果だけを見せる
- 取り消した受注は消さない（状態を「取消」にする） … **サーバの担当**。過去の伝票から参照されるので消せない
- 保存の検証は同じ定義でサーバでも回す … **サーバの担当**（`formValidator`）。画面の検証は親切であって守りではない（API を直接叩けば通る）
- 役割で隠したものは API でも役割を見て止める … **枠組みの外（hatake は持たない）**（`authz`）。画面の roles は見せ方だけ。認可は枠組みが持たないので、自分で書く
- 役割は社内ポータルが返す（sales / clerk / manager） … **枠組みの外（hatake は持たない）**。認証基盤の担当。名前だけこちらに合わせてもらう
- 同じ受注を2人が同時に直したら、更新日時が変わっていたら弾いて読み直させる … **サーバの担当**。先に保存した人の入力が黙って消えるのを止める
- 消費税の端数は切り捨て（明細ごとには丸めず、伝票単位で1回だけ計算する） … **枠組みの外（hatake は持たない）**（`taxRounding`）。丸めは業務の決めごとで、定義には書けない。画面もサーバも枠組みの `computeTax` を同じ引数で呼ぶ（3版同出力）ので数は一致するが、保存する値の正はサーバ
- 一括の取消は1件ずつ確定し、失敗した行だけ残す（成功した分は戻さない） … **サーバの担当**。締めた月の受注は取り消せないので、選んだ中に必ず通らない行が混ざる。 全部取り消すと「1件のために49件やり直し」になる
- 帳票は刷った時点の値を読む（締めた月は直せないので、確定後は変わらない） … **枠組みの外（hatake は持たない）**。締めの在り処はサーバ。締め前の月は刷るたびに数が動くが、それが業務の正
- 誰が・いつ・どの受注を直したかを残す … **枠組みの外（hatake は持たない）**（`auditLog`）。画面は押した結果しか知らない
- 受注を確定しても誰にも知らせない（出荷指示は別のタイミング） … **枠組みの外（hatake は持たない）**。出荷指示を投げるのは基幹システム側の都合。画面からは通知しない

> 「枠組みの外」「サーバの担当」と書いてあるものは、**画面側に実装しない**（画面には結果だけを出す）。判断そのものを Dart / TypeScript で書き始めない。
