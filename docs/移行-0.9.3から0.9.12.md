# 見本3本を 0.9.3 → 0.9.12 に上げた記録

> **中身**: 実際に上げてみて、**何が起きて何が起きなかったか**。
> **読むとき**: 自分の案件を上げるとき、どこを見ればいいかの当たりを付けるため。
> 手で直す所の一覧は枠組み側の
> [0.9.3 → 0.9.14 の上げ方](https://github.com/ASIL-E-Hatake/hatake/blob/main/docs/guide/migration-0.9.14.ja.md)
> （0.9.14 で破壊的変更が1つ増えたので、手引きは名前ごと引き継がれています）。

この間に**破壊的な変更が4つ**入っています。上げる前は身構えていましたが、
**実際に直した所は1か所もありませんでした**（枠組み側に1件、不具合が見つかりました）。

## 結論から

| | 直した所 |
|---|---|
| 定義（YAML） | **0 か所** ── 3本とも警告ゼロのまま通った |
| Flutter（Dart） | **0 か所** ── 3本とも `analyze` clean |
| Java（2本目のサーバ） | **0 か所** ── 読むだけで組み立てていない |
| **Node（1本目のサーバ）** | **1 か所** ── `page.keyField` → `page.keyFields[0]` |
| 参照の差し替え | 10ファイル（`v0.9.3` → `v0.9.12`） |

**直したのは、枠組みの型を自分で読んでいた1行だけ**でした。

## なぜ何も壊れなかったか

破壊的変更の4つは、**どれも案件側が触らない所**でした。

| 変更 | 当たる条件 | 見本は |
|---|---|---|
| `keyField` → `keyFields` | 画面を Dart / Java から**組み立てている** | 定義は YAML。組み立てていない |
| `toCsv` の引数追加 | CSV を**自分で書き出している** | 枠組みの `type: export` を使っている |
| `ColumnDefinition` に `options` | 列を**組み立てている** | 同上 |
| Java の record 2つ | 正式コンストラクタを**直に呼んでいる** | 読むだけ（`AppParser` で解析） |

### ただ1か所だけ当たった所

1本目の Node サーバが、解析後のモデルから鍵の名前を読んでいました。

```js
// 前
const key = page.keyField;          // undefined になる
// 後
const key = page.keyFields[0];      // 1つの列で決まるマスタなので先頭だけ
```

**壊れ方が分かりにくい**のが要点です。`undefined` がそのまま SQL の列名を作る所に
流れ、`Cannot read properties of undefined (reading 'replace')` という
**枠組みと無関係に見えるエラー**でサーバが 500 を返しました。
定義の検証も Flutter の解析も通っていたので、**API を叩くまで出ませんでした**。

とくに効いたのが **`findByKey(Object key)` の口が変わっていない**ことです。
1件を指す項目が1つの画面には、いままでどおり素の値が渡るので、
**Repository の実装は1行も直りません**。

> つまり「**YAML で定義を書いて、Repository を実装している**」という
> 枠組みが想定している使い方をしているかぎり、破壊的変更は当たりません。
> 当たるのは、枠組みの内部の型を**自分で組み立てている**場合だけです。

## 見つけた不具合（1件）

**上げたときにだけ出ました。** 網羅アプリのシナリオが3件まとめて止まりました。

```
シナリオに知らないキーが 3 件あります:
  - cases[0].expect.$comment: 知らないキー "$comment"
```

`$comment` は**読む人へのひとこと**で、シナリオの束にも1件にも書けます。
ところが「確かめたいこと」（`expect`）の中だけ許していませんでした。
0.9.6 で「シナリオの知らない鍵で止める」を入れたときの**作り込み不足**です。

**止める理由が無い所で止めると、道具そのものが信用されなくなります。**
枠組み側を直しました（覚え書きはどこに書いてもよい）。

> これが、上げてみないと出ない種類です。**単体試験は全部緑のまま**でした。

## 探し方（1行で当たりが付く）

```bash
grep -rn "keyField" apps/ --include=*.js --include=*.mjs --include=*.ts   --include=*.dart --include=*.java | grep -v keyFields
```

**言語を絞らないこと。** 最初 `.dart` と `.java` だけを見て「当たり無し」と判断し、
**Node サーバの1行を見落とした**まま先に進んでしまいました。

## 上げる手順（実際にやった順）

```bash
# 1. 参照を差し替える
#    apps/*/flutter-src/pubspec.yaml      … git の ref
#    apps/*/node-src/package.json         … Release の tgz
#    apps/order-entry-prj/java-src/build.gradle … JitPack の座標
#    hatake.version                       … 案件をまたぐ版の控え
# 2. 定義を先に見る（**動かす前にここで出る**）
npx hatake validate apps/<案件>/definitions/app.yaml --strict
npx hatake check    apps/<案件>/definitions/app.yaml
# 3. 取り直してコードを見る
flutter pub get && flutter analyze
# 4. 値のシナリオ（動く環境が要らない）
npx hatake run apps/<案件>/definitions/app.yaml --page <画面> --scenario <紙>
# 5. 動く環境が要るもの（API・画面）
bash tools/run-tests.sh
```

**2 → 4 の順が大事**です。定義の検証は環境が要らないので、
ここで止まるものを先に潰すと、後の手戻りが減ります。

ただし **5 を省いてはいけません**。今回ただ1つの直しは、
**5 まで来て初めて**出ました（2〜4 は全部通っていた）。

## 上げるだけで良くなった所（手で直していない）

- **詳細画面の明細が表で出る**。前は `[{orderNo: SO-1, lineNo: 1}]` と1行で出ていた
- **詳細画面と CSV が、一覧と同じ字になる**（`shipped` ではなく「出荷済」）
- **`hatake openapi` が app 1枚から全画面ぶんを出す**

| 案件 | 出る道 | 型 |

| 2本目（受注入力） | 3 本 | 16 個 |

## ついでに新しい機能を当てた所（2本目）

上げたあとスクリーンショットを見たら、**詳細画面の受注状態が `shipped`** のままでした。
0.9.4 で「詳細画面も選択肢の名前を引く」ようにしたのに直っていない ── と思いきや、
**その画面に選択肢が書かれていなかった**のが理由でした。

同じコード表が定義の**2か所**に書かれていて、詳細画面と帳票には無かったのです。
0.9.5 の語彙（`app.vocabularies`）がちょうどこのための機能なので、当てました。

```yaml
app:
  vocabularies:
    - name: orderStatus
      options:
        - { value: shipped, label: 出荷済 }
        …
```

使う所は名前で指すだけです（`optionsOf: orderStatus`）。撮り直したら
**「出荷済」**になりました。定義の重複も2か所 → 1か所になっています。

> **上げただけでは直りません。** 枠組みが「引ける」ようになっても、
> 引く相手を書いていなければ出ません。上げたあとに**画面を見る**のが要ります。
