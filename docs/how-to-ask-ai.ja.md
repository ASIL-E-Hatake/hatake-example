# 人が AI に何をするか（hatake を使うときの手順）

hatake の定義を書くのは AI。**その AI に依頼を出すのは人**。この紙は、その人が何を
用意して、何を決めて、何を投げるかをまとめたもの。

大事なことを先に:

> **人にしか書けない紙が2枚ある。** 案件の説明と、案件の前書き（`hatake.project.yaml`）。
> ここを AI に埋めさせると、**それっぽいけど誰も決めていないこと**が設計書として残る。

---

## 全体の流れ

```
[人] 案件の説明を書く（普通の日本語でいい）
  ↓
[AI] hatake where --from  … 枠組みの外を仕分ける（認証・締め処理・採番…）
  ↓
[人] 前書き（hatake.project.yaml）を育てる ← 下書きは AI が起こす
  ↓
[AI] 定義を書く → hatake check で自分で読み返す
  ↓
[人] hatake ask が返した問いに答える ← ここが人の本番
  ↓
[AI] 答えを前書きに書く → 問いが消える
```

人の仕事は**3か所だけ**。あとは道具が答える。

---

## 1. 案件の説明を書く（人）

普通の日本語で、知っていることを書き出すだけ。書式は要らない。

**書いたほうがいいもの:**

- どんなシステムか・誰が使うか
- 管理したいもの（項目名は業務の言葉のままでいい）
- **できないこと・やらないこと**（これが一番大事。書かないと AI は書ける方に倒す）
- 決まっていないこと（「たぶん残す」でいい）

見本: [社内マスタメンテナンスの例](../apps/master-maintenance-prj/docs/1-要件定義/案件の説明.md)

## 2. 枠組みの外を仕分ける（AI に投げる）

```
docs/1-要件定義/案件の説明.md を hatake where --from で仕分けて、
**枠組みの外のもの**を教えて。
```

認証・締め処理・採番・承認フロー・監査は **hatake が持たない**。ここで「外」と出たものを
定義に書かせようとすると、AI は画面の中に業務ロジックを書き始める。

外のものは、前書きの `premises` に「**できないこと**」として残す。

## 3. 前書きを育てる（人）

`hatake.project.yaml` は**定義を書く前に AI に読ませる1枚**。

| 節 | 何を書くか | 機械が見るか |
|---|---|---|
| `system.what` / `users` | 何のシステムか・誰が使うか | 見ない（人と AI が読むだけ） |
| `system.premises` | **できないこと** | 見ない |
| `glossary` | 業務の言葉 → 定義に書く名前 | **見る**（定義と突き合わせる） |
| `logic` | 業務ロジックの**置き場**（中身は書かない） | **見る** |
| `naming` | 名前の形（camelCase など） | **見る** |

下書きは AI に起こさせていい:

```
hatake project --draft --from docs/1-要件定義/案件の説明.md で下書きを起こして。
ただし**私が言っていないことは書かないで**。
```

**下書きは薄い。** 資料の見出しから拾える所しか拾わないので、ほとんど空で返ってくる。
育てるのは人。それでいい（想像で埋まって返ってくる方が困る）。

### 決めごとは「守れるものだけ」書く

`naming.suffix` のような縛りは、書くと**毎回助言が鳴る**。守れないものを書くと鳴りっぱなしに
なって、そのうち誰も助言を読まなくなる。

実例: `naming.suffix.number: Amount` と書いたら、`creditLimit` を `creditLimitAmount` に
しろと言われ続けた。業務の言葉から離れるのでやめた。

### 辞書の見出しは広く取りすぎない

`glossary` の `term` と `avoid` は**部分一致で効く**。「区分」を見出しにすると
「在籍区分」まで巻き込む。

## 4. 定義を書かせる（AI に投げる）

```
definitions/hatake.project.yaml を読んでから、<やりたいこと> を定義に書いて。

書けたら hatake check --project にかけて、**警告ゼロ**になるまで直して。
**助言（好み）は当てる前に何を当てるか教えて**。
```

3つ必ず入れる:

1. **前書きを先に読ませる** — 読ませないと用語が揺れる
2. **警告ゼロまで** — 警告は事実なので、直すのに業務の判断は要らない
3. **助言は勝手に当てさせない** — 助言は好みで、案件によって答えが違う

## 5. 問いに答える（人・ここが本番）

`hatake ask` が返すのは、**定義に書けないのに、画面がある以上決まっていないと嘘になること**。

- 同時に直したらどちらが残るか
- 一括が途中で失敗したら
- 消したものを残すか
- 画面の検証をサーバでも見るか
- 役割はどこから来るか
- 監査を残すか

**AI には答えられない。** 答えると「それっぽいけど誰も決めていない設計」ができる。

答えたら前書きの `logic` に1行足して `answers: [<印>]` を付ける。次から同じ問いは出ない。

> 印（id）は `hatake ask --kinds` で引ける正しいものを使う。それっぽい名前を書くと
> 「そんな問いはありません」と落とされる（落とされるのが正しい）。

---

## やってはいけないこと

| | なぜ |
|---|---|
| 前書きを AI に想像で埋めさせる | 案件のことは人しか知らない。埋まった紙は嘘の設計書になる |
| 問いに AI が答える | 業務の判断。答えは案件ごとに違う |
| 「外」と出たものを定義に書かせる | 画面の中に業務ロジックが入る。hatake が壊れる |
| 助言を全部当てさせる | 助言は好み。当てるほど良い定義になるわけではない |
| 定義を手で書く | 書けるが、**手で書くと前書きと突き合わせが効かない**（AI に書かせて道具にかける方が速い） |
