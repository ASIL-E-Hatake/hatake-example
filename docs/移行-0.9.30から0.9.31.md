## VS Code 拡張で見本を開いてみた

見本の定義4枚（30分サンプル・マスタメンテ・受注入力・機能網羅）を、拡張機能と同じ部品に
通した。

- ツリーは4枚とも作れた（画面 18・行 208）。**どの行も定義のその場所を指している**
  （「↗」で YAML に飛べる）

**ただし、「人が決めること」が見本の紙と合わない**。拡張機能は定義だけを `check` に渡していて、
前書き（`hatake.project.yaml`）を渡していない。そのため、**前書きで答えた問いがもう一度出る**。

| 案件 | 拡張機能が出す問い | 見本の紙（前書きつき） |
|---|---|---|
| 受注入力 | 8 件 | **1 件**（`state-owner`） |
| マスタメンテ | 9 件 | **0 件** |
| 機能網羅 | 11 件 | **0 件** |

あわせて、前書きの名前の決めごとから出る好み（受注入力で3件）も出ない。「人が見る答えと AI が
見る答えは同じ」が、**前書きのある案件では崩れている**。人が見る道具なのに、答え済みの問いが
並ぶのはいちばん困る形なので、**枠組みに返す**（定義から近い前書きを探して `project` に渡す。
問題の一覧も同じ）。

直るまでは、受注入力の「人が決めること」は
[残っている問い](../apps/order-entry-prj/docs/2-設計/出力-残っている問い.txt)のほうを正にしてください。
見本の手引き（[AI で作る道筋](AIで作る道筋.md)）に拡張機能の画面を載せるのも、直ってからにします
（今撮ると、答え済みの問いが並んだ絵になる）。

## 初見試験

同じ課題・同じモデル（claude-sonnet-5-5）で、6回ずつ回した。Claude Code は 2.1.292 → 2.1.293 に
上がっている（差は hatake だけのせいではない）。成績表は
[v0.9.31](../evals/results/v0.9.31/成績表.md)（前の版との比較つき）。

| | v0.9.30 | v0.9.31 |
|---|---|---|
| 合格 | 6 / 6 | 6 / 6 |
| 断られた引数（のべ）・うち近い名前つき | 2 ・ 2 | 2 ・ 2 |
| `reference` が空振り（のべ） | 2（`immutable`・`editable`） | 1（`editOnly`） |
| `where` の「載っていない」（のべ） | 0 | **1**（作成後に変更不可の項目） |
| 枠組みの中身を読みに行った試行 | 0 | **1**（仕様書を grep） |
| 名前だけの npx ・答えが大きすぎた試行 ・`examples` の空振り | 0 ・ 0 ・ 0 | 0 ・ 0 ・ 0 |
| 往復（平均） | 20 | 20 |

AI の側は何も変えていないので、合否も往復も同じ。

**前の回に見えた「意味で引く」が、今回いちばんの詰まりになった**。どれも「作ったあとは
変えられない項目」を書こうとして止まっている（正しいのは `readOnlyWhen`）:

- `hatake_reference` に `editOnly` を引いて空振り（前の回は `immutable` / `editable`）
- `hatake_where` に「作成後に変更不可の項目」を引いて「載っていない」
- 1試行は道具で引けず、`node_modules/@hatake-fw/api/spec` の仕様書を grep して `readOnlyWhen` と
  `$isNew` を探し当てた

キーの名前でも値でもないので、今の引き方では当たらない。**意味の近いキーを添える表**
（`readonly` / `immutable` / `editable` / `editOnly` → `readOnlyWhen` …）を `reference` と `where` の
両方に効かせたい。枠組みに返す（前の回の候補の優先度を上げる）。
